＃＃ 概述

以下是设计 Lexicon 模式的一些推荐约定和最佳实践。

名称大小写约定：

- 模式和属性：模式和名称使用“lowerCamelCase”大写（而不是“UpperCamelCase”、“snake_case”、“ALL_CAPS”等）。
- API 错误名称：`UpperCamelCase`
- 固定字符串（例如“knownValues”）：“kebab-case”

可接受的字符：

- 字段名称应坚持与模式名称（NSID 名称段）相同的字符集：ASCII 字母数字，第一个字符不是数字，没有连字符，区分大小写
    - 在某些情况下，例外可能是合理的，例如在现有外部模式中保留名称
    - 数据对象在任何嵌套级别都不应包含以“$”开头的模式指定字段名称；这些是为未来的协议级扩展保留的

## 命名约定

- 对“记录”模式使用单数名词
    - 例如“帖子”、“喜欢”、“个人资料”
- 对“查询”和“过程”端点使用“动词-名词”
    - 例如`getPost`、`listLikes`、`putProfile`
    - “query”端点的常见动词有：“get”、“list”、“search”（用于全文搜索）、“query”（用于灵活匹配或过滤过滤）
    - “procedure”端点的常用动词：“create”、“update”、“delete”、“upsert”、“put”
- 使用“subscribe-plural-noun”表示“订阅”
    - 例如`订阅标签`
- “permission-set”模式命名约定尚未建立，但可能有“auth”前缀（例如，“authBasic”）
- 如果端点是实验性的、不稳定的或不打算实现互操作性，请在 NSID 名称中指出
    - 例如，在 NSID 层次结构中包含 `.temp.` 或 `.unspecced.`
- 避免与流行的编程语言约定冲突的通用名称
    - 例如，避免使用“default”或“length”作为模式名称

## 文档

- 为每个“主”模式定义添加描述（记录、API 端点等）
    - 对于API端点，在描述中提及是否需要身份验证，以及如果身份验证是可选的，响应是否会个性化
- 为可能不明确的字段和属性添加描述。这对于具有“uri”或“cid”等通用名称的字段尤其重要：CID 是什么？

NSID命名空间分组：

- 许多应用程序和项目将具有多个不同的功能或特性，并且所有类型的模式都可以在 NSID 层次结构中表示该分组
    - 例如 `app.bsky.feed.*` 、 `app.bsky.graph.*`
- 非常简单的应用程序可以包含单个 NSID“组”下的所有端点
- 使用“.defs”模式进行定义，这些定义可能被同一命名空间中的多个模式或第三方重用
    - 例如`app.bsky.feed.defs`
    - 将它们放在单独的架构文件中意味着弃用或删除其他架构文件不会影响重用
- 避免组、名称和定义之间的冲突和混淆
    - 例如 `app.bsky.feed.post#main` 与 `app.bsky.feed.post.main` 或 `com.example.record#foo` 和 `com.example.record.foo`
    - 或定义“app.bsky.feed”（作为记录）和“app.bsky.feed.post”（将“app.bsky.feed”作为一个组）

## 其他指南

- 适当时指定字符串字段的格式
- 如果记录中的字符串字段没有格式类型，则它们几乎总是具有最大长度
    - 不要冗余地指定格式和长度限制
    - 如果出于语义或视觉原因限制字符串的长度，则应使用字素限制来确保人类语言之间的一定程度的一致性。在这些情况下，还应添加数据大小（字节）限制。建议使用 10 到 20 字节与 1 个字素的比率。
- 字符串和字节记录数据类型适用于数据大小受限的用例。对于较大尺寸的文本或二进制数据，应使用 blob 引用。这可以包括较长形式的文本和结构化数据。
- 枚举集是“封闭的”，并且在不违反模式演化规则的情况下无法更新或扩展。因此，几乎应该始终避免使用它们。
    - 对于字符串，“knownValues”提供了更灵活的替代方案
- 字符串“knownValues”可以包括简单的字符串常量，或者可以包括对“令牌”的模式引用（例如，字符串“com.example.defs#tokenOne”）
    - 代币提供了扩展机制，并且适用于具有主观定义或可能随着时间的推移而扩展的值
    - 有关两个对比实例，请参阅“com.atproto.moderation.defs#reasonType”和“com.atproto.sync.defs#hostStatus”，前者可扩展，后者更具约束性
- 利用可重用的定义，例如“com.atproto.repo.strongRef”（用于记录的版本化引用）或“com.atproto.label.defs#label”（在数组中，用于水合标签）
- 将帐户标识符作为参数（例如查询参数）的 API 端点应使用“at-identifier”，以便客户端在只有帐户句柄时可以避免调用“resolveHandle”
- 记录模式应始终使用持久标识符（DID）来引用其他帐户，而不是句柄
- API端点应始终指定带有“编码”的“输出”，即使它们没有有意义的响应数据
    - 一个好的默认值是“application/json”，其架构是一个没有定义属性的对象
- 可选的“boolean”字段的措辞应使“false”成为默认值和预期值
    - 例如，如果端点可以返回“foo”和“bar”的混合，并且常见行为是包含“foo”但不包含“bar”，则控制参数应命名为“excludeFoo”（默认为“false”）和“includeBar”（默认为“false”），而不是“excludeBar”（默认为“true”）
- 内容哈希 (CID) 可以表示为字符串格式或二进制编码 (`cid-link`)
    - 在大多数情况下，包括记录之间的版本化引用，建议使用字符串格式。
    - 二进制编码主要用于协议级机制，例如 firehose。

## 词汇演变

所有词典都应该能够随着时间的推移灵活地扩展和演变，而不违反词典模式演变规则。对于记录模式尤其如此。鉴于atproto的分布式存储模型，开发人员没有可靠的机制来更新网络中的所有数据记录。扩展可以来自原始设计者，也可以来自其他开发人员和项目。

实验模式和项目可以使用变体 NSID（例如，在名称层次结构中包括“.temp.”）在实时网络中进行开发，而无需提交稳定的记录数据模式。

通过声明新模式可以进行主要的非向后兼容模式更改。当前的命名约定是在原始名称后附加“V2”（或“V3”等）。

设计建议以使模式能够灵活适应未来的演变和扩展：

- 不要将数据字段或 API 参数标记为“必需”，除非它们确实是功能所必需的
    - 根据演化规则，“必填”字段不能成为可选字段或弃用字段
- 你可以向架构添加新的“可选”字段，而无需更改向后兼容性或需要 V2 架构，但不能添加新的“必需”字段
- 使用包含单个元素/字段的对象类型而不是数组中的原子数据类型，以允许将来包含其他上下文
    - 例如，在列出帐户 (DID) 的 API 响应中，返回一个对象数组，每个对象都有一个列出 DID 的“帐户”字段，而不是字符串数组
- 使联合在几乎所有情况下“开放”，以允许将来添加类型或值
    - 开放联合可以作为第三方的扩展机制，包含自定义的数据类型

## 设计模式

- “查询”API 端点的分页有一个基本约定：
    - 查询参数包括可选的“limit”（整数）和可选的“cursor”（字符串）
    - 输出正文包括可选的“光标”（字符串）和必需的响应对象数组（具有上下文特定的复数字段名称）
    - 初始客户端请求未定义“光标”。如果响应包含“cursor”，则有更多结果可用，客户端应使用新的“cursor”再次查询以获得更多结果
    - “limit”值是上限，响应可能包含更少（甚至零）的结果，但仍然有更多结果可用。响应中缺少“光标”表明分页已完成。如果响应集中的项目被逻辑删除或以其他方式从响应集中过滤，则响应集中可能会删除这些项目。
- 还有一个支持“排序”和回填游标的订阅端点约定：
    - 端点有一个可选的“cursor”查询参数（整数）
    - 所有核心消息类型都包含“seq”字段（整数）。消息的“seq”单调增加，尽管可能有间隙。
    - 如果未提供“cursor”，服务器将从当前点开始返回新消息
    - 如果提供了“cursor”，服务器将尝试返回以匹配的“seq”开始的历史消息，继续到当前流
    - 如果“光标”位于未来（高于当前序列），则返回错误并关闭连接
    - 如果“cursor”早于最早的可用消息（或者为 0），则服务器返回名称为“OutdatedCursor”的信息消息，然后返回从最早的可用消息开始的消息
- API 响应中的常见模式是包含数据记录的“水合视图”。例如，当查看帐户的个人资料时，响应可能包括任何媒体文件的 CDN 或缩略图 URL、审核标签、全局聚合和特定于查看者的社交图上下文。
    - 对于详细视图，最佳实践是逐字包含原始记录，而不是使用字段超集定义新架构。这更容易维护（不能忘记更新字段），并确保包含任何非架构扩展数据。
    - 特定于查看者的元数据应该是可选的，并且可以在描述中指示或分组在子对象下。这使得模式可以在“公共”和“登录”视图之间重用，并且更清楚什么信息何时可用。
    - 对于应用程序开发人员来说，一个有用的模式是确保有一个 API 端点接受对记录的引用（例如，AT URI 或等效项；或多个引用）返回水合数据对象。
- “app.bsky.richtext.facet”系统可用于以比全功能标记语言更简单、更安全的方式注释短文本字符串
    - 有关更多详细信息，请参阅[“为什么在 Bluesky 中使用 RichText 构面”](https://www.pfrazee.com/blog/why-facets)
    - 特征类型系统是一个开放联合，可以通过其他类型进行扩展
    - Markdown 也可用于长文本
- 扩展或补充记录的一种模式是在同一帐户存储库中定义具有相同记录密钥和不同类型（集合）的“sidecar”记录。
    - Sidecar 记录可以由原始 Lexicon 设计者或独立开发人员定义和管理。
    - sidecar 记录可以更新（变异），而不会破坏对原始记录的强引用。
    - Sidecar 上下文可以包含在 API 响应中。
- 由于 atproto 帐户可以灵活地与网络中的任何应用程序一起使用，因此哪些帐户参与特定应用程序模式可能不明确。如果该模式存在已知的代表性记录类型，并且客户为活动帐户创建此类记录，则可以澄清这一点。删除此记录可以作为指示用户不再活跃的一种方式。如果记录具有单个已知实例（固定记录键），则此方法效果最佳。
    - 例如，应用程序特定的“配置文件”或“声明”记录可以指示该帐户至少登录过关联的应用程序一次，即使记录为“空”。
    - 回填服务可以使用给定的信令记录枚举网络中的所有帐户，并且还可以将该记录的删除处理为该模式的停用。
    - 强烈建议新的应用程序模式使用此设计模式。
