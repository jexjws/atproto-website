## 使用 lex 安装词典

我们的 SDK 每个都安装了一个“lex”工具，可让您生成类型安全的客户端，该客户端知道每个 AT 端点需要哪些参数。

### 打字稿

首先，安装`@atproto/lex`包：

<NpmInstall />

这提供了“lex”命令，您可以使用该命令将 Lexicons 安装到本地项目中：

<LexInstallLexicons />

这将创建：

- `lexicons.json` - 清单跟踪已安装的 Lexicons 及其版本 (CID)
- `lexicons/` - 包含 Lexicon JSON 文件的目录

最后，从安装的 Lexicons 生成 TypeScript 模式：

<LexBuild />

这会将 TypeScript 文件写入“./src/lexicons”。运行“lex build”后，调用方法就是针对生成的定义的类型化“client.call”：

<ClientUsageTs />

有关使用“lex”的更多指导，请参阅[自述文件](https://github.com/bluesky-social/atproto/tree/main/packages/lex/lex#lexicon-schemas)。

## XRPC 方法

“main”定义是一个方法的 Lexicon 描述了三种 XRPC 调用之一：

- **`query`** — 通过 HTTP `GET` 读取查询字符串中的参数。有关端到端示例，请参阅[读取数据](/guides/reading-data)。
- **`procedure`** — 一个副作用调用，通过 HTTP `POST` 提供，作为 JSON 正文（或其他 MIME 类型，如果声明）输入。请参阅[写入数据](/guides/writing-data)。
- **`订阅`** — 服务器推送的带有 DAG-CBOR 帧的 WebSocket 流，用于 Firehose。

Each method is reachable at `/xrpc/<nsid>` on whatever service implements it — `app.bsky.actor.getProfile` lives at `https://public.api.bsky.app/xrpc/app.bsky.actor.getProfile`. The NSID *is* the URL path.

参数、输入主体和输出都在编译时进行类型检查，并在运行时根据 Lexicon 形状进行验证。

## 使用 .internal TLD

NSID 使用反向 DNS 查找——“app.bsky.*”在“bsky.app”下解析，“com.atproto.*”在“atproto.com”下解析。但对于同一运营商的组件之间的**服务到服务调用，没有可发布或解析的公共模式。

对于这些，您可以使用以“internal.”为前缀的 NSID，利用永远无法注册的 [`.internal` 作为保留 TLD](https://www.iana.org/assignments/special-use-domain-names/special-use-domain-names.xhtml)。例如，参考实现包括 [`internal.bsky.actor.getProfiles`](https://github.com/bluesky-social/atproto/blob/main/lexicons/internal/bsky/actor/getProfiles.json)，它是 `app.bsky.actor.getProfiles` 的变体。

这给你：

- **内置 SDK 排除。** `@atproto/lex` 中的 codegen 过滤器将 `*.internal.*` 视为规范排除模式，因此内部端点永远不会出现在您发布的客户端 SDK 中。
- **All of the XRPC machinery.** Same codegen, typed handlers, request/response validation, inter-service auth, and `/xrpc/<nsid>` routing, but without committing the endpoint to your public protocol surface.

每当 XRPC 方法为您自己的基础设施进行管道检查时，请使用“internal.*”：特定于一个调用者、管理或操作查询的优化，或者您不希望第三方实现者有义务支持的任何内容。
