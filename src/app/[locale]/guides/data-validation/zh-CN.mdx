# 数据验证

有些软件不需要太担心 Bluesky 或 atproto 模式验证。例如，客户端应用程序和机器人通常可以假设他们从 Bluesky API 接收的数据是有效的，并且当他们尝试创建记录时，PDS 负责双重检查架构验证。

直接从事件流（firehose）消费的软件应该更加小心。设计新工具或巧妙破解的开发人员应该意识到有关数据验证的一些期望和硬性限制。

如果单个记录由于任何原因未能验证，则应忽略整个记录，但应处理同一存储库中的其他记录。如果存储库提交数据或存储库结构（“MST”）存在问题，则应将存储库标记为无效，但旧内容不需要取消索引或清除。一旦收到新的有效提交，存储库就应再次标记为有效。此逻辑主要与 feed 生成器、AppView 和审核服务相关，所有这些都可能从 Firehose 中消耗。


## 建议的数据限制

以下是非正式的指导方针，主要是为了传达数量级的期望，并且可能会随着时间的推移而演变。它们不是 atproto 规范的一部分，但如果您在这里突破限制，您现在或将来可能会遇到互操作性问题。

**CBOR 记录大小：** 尝试将单个记录保持在几十 KB。如果您需要存储更多数据，甚至是文本数据，请考虑使用 blob。合理的最大记录大小限制（MAX_CBOR_RECORD_SIZE）为 1 MiByte（1 mebibyte，或 1,048,576 字节）。请注意，截至 2025 年 8 月，“subscribeRepos”词典将“#commit”消息块大小限制为 2,000,000 字节（不是兆字节），因此每次提交只能创建或更新一条 1 MiByte 记录。

请注意，事件流（消防水带）“帧”可能由多个记录组成，一般建议对 CBOR 解析设置更大的限制，大约为 4-5 MB。

**JSON 记录大小：** CBOR 编码对于记录来说是“规范的”，因此仅关注该编码是有意义的。但有时对 JSON 编码大小也有限制是件好事。合理的限制（“MAX_JSON_RECORD_SIZE”）是 2 MiByte（2,097,152 字节）。

**一般字符串长度：** 记录中字符串的总长度限制，包括具有和不具有 Lexicon 指定的字符串长度的字符串。以字节为单位（UTF-8 编码）。应尽量将这些大小控制在最多数十 KB。对于上限 (MAX_RECORD_STRING_LEN)，仅依赖整体 CBOR 记录大小限制是合理的。值得注意的是，一些早期的实现有 8 KB（8192 字节）的限制。

**一般“字节”长度：** 与字符串限制相同，但适用于二进制数据（“MAX_RECORD_BYTES_LEN”）。建议依赖整体 CBOR 记录大小限制。与总体记录大小一样，如果需要超过几十 KB，建议使用 blob。

**CID 二进制编码大小：** 建议总体限制 (`MAX_CID_BYTES`) 为 100 字节。

**容器嵌套深度：** 例如，一个数组内部有多少层map等。如果你的CBOR或JSON解析库支持限制，默认的可能就可以了。合理的限制（MAX_CBOR_NESTED_LEVELS）是 32 层嵌套。

**容器元素计数：** 例如，映射中有多少个键，或数组中有多少个元素。如果您的 CBOR 或 JSON 解析库支持限制，则默认值可能就可以了。合理的限制 (MAX_CBOR_CONTAINER_LEN) 是 128 x 1024 = 131,072 个元素。

**对象密钥字符串长度：** 例如，对象的任何密钥中允许有多少个字节（UTF-8编码）。如果您的 CBOR 或 JSON 解析库支持限制，则默认值可能就可以了。合理的限制 (MAX_CBOR_OBJECT_KEY_LEN) 是 8 KB (8192)。

**整数：** 正如 [atproto 规范](https://atproto.com/specs/data-model#data-types) 中提到的，强烈建议保持整数值“64 位浮点安全”的最佳实践，这意味着将它们限制为 53 位精度。这确保了与 JavaScript 的兼容性，而不会损失数字精度。具体值为“MAX_SAFE_INTEGER：9007199254740991”和“MIN_SAFE_INTEGER：-9007199254740991”。
