# 数据模型

atproto 中的记录和消息以一致的方式存储、传输、编码和验证。核心“数据模型”支持二进制（CBOR）和文本（JSON）表示。 {{ className: '领导' }}

当数据需要进行身份验证（签名）、引用（通过内容哈希链接）或高效存储时，它会以简洁二进制对象表示形式 (CBOR) 进行编码。 CBOR 是一个大致基于 JSON 的 IETF 标准。 atproto 数据模型中使用的 CBOR 的特定标准化子集称为 [DRISL](https://dasl.ing/drisl.html)（它是 [DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/) 的后继者）。所有 DRISL-CBOR 数据都是有效的 CBOR，并且可以使用任何 CBOR 库读取。使用正确的规范化规则编写或严格验证 CBOR 有时需要额外的配置或特殊的 CBOR 实现。 {{ className: '领导' }}

atproto 的模式定义语言是 [Lexicon](/specs/lexicon)。其他较低级别的数据结构，例如 [repository](/specs/repository) 内部结构，未使用 Lexicons 指定，但使用相同的数据模型和编码。

不同的数据块称为**节点**，当以二进制 (DRISL-CBOR) 编码时会生成 **块。** 节点可能具有内部嵌套结构（映射或列表）。节点可以通过字符串 URL 或 URI 相互引用，就像 Web 上的常规 JSON 一样。它们还可以通过哈希相互强引用，称为 **链接。** 一组链接的节点可以形成更高级别的数据结构，例如 [Merkle 树](https://en.wikipedia.org/wiki/Merkle_tree) 或 [有向非循环图 (DAG)](https://en.wikipedia.org/wiki/Directed_acircy_graph)。链接还可以引用任意二进制数据（blob）。

与 URL 不同，哈希引用（链接）不会对可以找到内容的特定网络位置进行编码。位置和访问机制必须通过协议级上下文来推断。哈希引用确实具有“自认证”属性，这意味着可以根据链接哈希来验证返回的数据。这使得重新分发内容和信任副本成为可能，即使来自不受信任的一方也是如此。

链接被编码为[内容标识符](https://dasl.ing/cid.html) (CID)，它具有二进制和字符串表示形式。 CID 包括元数据代码，指示它是否链接到节点 (DRISL-CBOR) 还是任意二进制数据。下面描述了 atproto 中使用 CID 的一些附加限制。

在 atproto 中，对象节点通常包含一个字符串字段“$type”，用于指定其 Lexicon 模式。数据大多是自描述的，可以以与模式无关的方式进行处理（包括解码和重新编码），但如果没有现有模式或提前知道模式，则无法完全验证。

## 与 DASL 和 IPLD 的关系

atproto 数据模型与 [DASL](https://dasl.ing/) 一致，这是一种哈希链接数据结构的规范。实现 atproto 时可以使用 DASL 库和工具。 DASL 本身是[星际链接数据 (IPLD)](https://ipld.io/docs/data-model/) 的子集。

IPLD 指定了一种名为 **DAG-JSON** 的标准化 JSON 编码，但 atproto 在编码 JSON 数据时使用一组不同的约定。 atproto JSON 编码并非设计为字节确定性的，当数据需要加密签名或散列时，使用 CBOR 表示形式。

## 数据类型

`blob` 用于对文件（例如图像）的引用。它包括基本元数据，如 MIME 类型和大小（以字节为单位）。

作为确保 Javascript 与默认类型兼容的最佳实践，“integer”应限制为 53 位精度。请注意，JSON 数字可以具有任意位数，但即使忽略 Javascript，“整数”也仅限于 64 位。

词典可以包含对各个字段的附加验证约束。例如，整数可以具有最大值和最小值。如果不访问相关的 Lexicon 模式，则无法针对这些附加约束来验证数据，但存在一个抽象意义上针对 atproto 数据模型验证自由格式 JSON 或 CBOR 的概念。例如，带有嵌套“$bytes”对象（带有布尔值而不是 Base64 编码字符串）的 JSON 对象可能是有效的 JSON，但在 atproto 数据模型下永远不会有效。

Lexicon 字符串字段可以具有与其关联的附加“格式”类型信息以进行验证，但与其他验证约束一样，如果没有 Lexicon 本身，则该信息不可用。

在 JSON 和 CBOR 表示形式中，以“$”开头的数据字段名称保留供数据模型或协议本身使用。例如，“$bytes”键名称（用于 CBOR 和 JSON）、“$link”键（用于 JSON CID 链接）或“$type”（用于指示记录类型）。实现应该忽略未知的“$”字段（以允许协议演变）。应用程序、扩展和集成不应使用或单方面定义新的“$”字段，以防止协议发展时发生冲突。

### 可空和 False-y

在 atproto 数据模型中，显式将映射字段设置为“null”与根本不包含该字段之间存在语义差异。 JSON 和 CBOR 都有相同的区别。

空或缺失字段也不同于“false-y”值，例如“false”（对于布尔值）、“0”（对于整数）、空列表或空对象。

### 为什么没有浮动？

CBOR 和 JSON 本身都支持浮点数，那么为什么 atproto 不遗余力地禁止它们呢？

IPLD 规范描述了在内容可寻址世界中使用浮点数时的[一些复杂性和尖锐边缘](https://ipld.io/docs/data-model/kinds/#float-kind)。简而言之，反序列化为机器本机格式，然后重新编码，并不总是一致的。这对于特殊值和极端情况来说绝对是正确的，但对于不太常见的架构上的“正常”浮点值来说甚至可能是正确的。

将来也许可以制定规则来确保浮点数的可靠往返编码，但目前我们不允许浮点数。

如果您的用例无法用整数代替浮点数，我们建议将浮点数编码为字符串甚至字节。这提供了安全的默认往返表示。

## `blob` 类型

对“blob”（任意文件）的引用在 atproto 中具有一致的格式，并且无需访问任何特定的 Lexicon 即可检测和处理。也就是说，可以在不知道架构的情况下解析节点并提取任何 blob 引用。

Blob 节点是具有以下字段的映射：

- `$type`（字符串，必需）：固定值`blob`。请注意，这不是有效的 NSID。
- `ref`（链接，必需）：对 blob 的 CID 引用，编解码器类型为 `raw`。在 JSON 中，像往常一样编码为 `$link` 对象
- `mimeType` （字符串，必需，非空）：blob 的内容类型。如果不知道，则为“application/octet-stream”
- `size`（整数，必需，正数，非零）：blob 的长度（以字节为单位）

还有一种已弃用的旧版 blob 格式，一些野外记录仍包含此格式的 blob 引用：

- `cid`（字符串，必需）：*string* 格式的 CID，而不是 *link* 格式
- `mimeType` （字符串，必需，非空）：与上面的 `mimeType` 相同

请注意，旧格式没有“$type”，只能解析已知的词典。实现在遇到旧格式时不应该抛出错误，但绝对不应该编写它们，并且仅部分支持它们是可以接受的。

## JSON 表示

Atproto 使用自己的 JSON 约定，而不是直接使用 DAG-JSON。主要动机是为 HTTP API 中的“链接”和“字节”提供更惯用和人类可读的表示形式。 DAG-JSON 规范本身提到它主要面向调试和开发环境，我们发现使用“/”作为字段键让开发人员感到困惑。

在 atproto 中使用 JSON 时，也不需要或强制执行诸如键排序之类的规范化：仅使用 DRISL-CBOR 作为字节可重现的表示。

大多数核心和复合类型的编码都是直接的，只有“link”和“bytes”需要特殊处理。

### `链接`

链接的 JSON 编码是一个具有单个键“$link”和字符串编码的 CID 作为值的对象。

例如，具有类型为“link”的单个字段“exampleLink”的节点将在 JSON 中进行编码，如下所示：

````
{
  “示例链接”：{
    “$link”：“bafyreidfayvfuwqa7qlnopdjiqrxzs6blmoeu4rujcjtnci5beludirz2a”
  }
}

````

为了进行比较，这与 DAG-JSON 编码非常相似，但用“$link”代替“/”（单字符，正斜杠）作为键名。

### `字节`

字节的 JSON 编码是一个具有单个键“$bytes”和带有 Base64 编码字节的字符串值的对象。 Base64 方案是 [RFC-4648，第 4 节](https://datatracker.ietf.org/doc/html/rfc4648#section-4) 中指定的方案，通常称为简单的“base64”。此方案不是 URL 安全的，并且 `=` 填充是可选的。

例如，具有类型为“bytes”的单个字段“exampleBytes”的节点将用 JSON 表示，如下所示：

````
{
  “示例字节”：{
    “$字节”：“nFERjvLLiw9qm45JrqH9QTzyC2Lu1Xb4ne6+sBrCzI0”
  }
}

````

为了进行比较，DAG-JSON 编码有两个嵌套对象，外键为“/”（单字符、正斜杠），内键为“bytes”，并且具有相同的 base64 编码。

## 链接和 CID 格式

[原始 IPFS CID 规范](https://github.com/multiformats/cid) 非常灵活。它支持多种哈希类型、指示链接内容“类型”的字段以及各种字符串编码选项。这些功能对于允许随着时间的推移而演变是有价值的，但为了最大限度地提高实现之间的互操作性，只允许特定的“祝福”CID 类型集。这些符合 [DASL CID](https://dasl.ing/cid.html) 规范。

atproto 中受祝福的 CID 格式是：

- CID 版本：1 (0x01)
- 编解码器：DRISL（0x71；也称为“dag-cbor”）用于链接到 DRISL-CBOR 数据对象，“raw”（0x55）用于链接到 blob
- 哈希类型：`sha-256` (0x12)，大小为 256 位（0x20 字节）
- 编码：DRISL-CBOR `cid-link` 字段中的二进制序列化，以及用于其他地方字符串编码的 `base32` （带有 `b` 前缀）

在某些情况下，例如存储库 MST 节点，使用 SHA-256 是一项稳定的要求。在其他情况下，例如引用媒体 blob，可能会存在一组随时间演变的“有福的”哈希类型。一方面需要在协议灵活性（采用改进的哈希值并删除较弱的哈希值）与确保整个协议实现生态系统中广泛且一致的互操作性之间取得平衡。

有多种方法可以在 atproto 对象中包含 CID 哈希引用：

- `link` 字段类型（词典类型 `cid-link`）。在 DRISL-CBOR 中，CID 通过在其二进制表示形式前加上“0x00”前缀来进行编码。用于表示 CID 的 CBOR 标记为 42。在 JSON 中，编码为“$link”对象（见上文）。
- `string` 字段类型，采用 Lexicon 字符串格式 `cid`。在 DRISL-CBOR 和 JSON 中，编码为简单字符串
- `string` 字段类型，Lexicon 字符串格式 `uri`，URI 方案 `ipld://`

## 使用和实施指南

使用已弃用/旧版“blob”格式时，建议以与常规“blob”引用相同的内部表示形式存储，但将“size”设置为零或负值。重新序列化时应检查此字段，以确保正确的往返行为并避免以正常对象格式编码零或负“大小”值。

[数据验证指南](/guides/data-validation) 中描述了验证和限制通用 atproto 数据的大小和结构的最佳实践，该指南并不是本规范的正式部分。

## 安全和隐私考虑

解析不受信任的 CBOR 内容时，可能会出现多种资源消耗攻击。建议使用能够自动防止巨大分配、深度嵌套、无效引用等的库。这对于用不具备强内存安全性的语言实现的库（例如 C 和 C++）尤其重要。请注意，高级语言经常包装用低级语言编写的解析器。

## 未来可能的变化

可以以一种或另一种形式支持浮动。

如果可以重写所有已知记录和存储库，则可以完全删除遗留的“blob”格式。

额外的散列类型可能包含在“有福的”CID 配置集中。
