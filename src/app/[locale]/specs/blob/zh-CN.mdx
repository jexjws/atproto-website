# 斑点

**Blob** 是与帐户存储库一起存储的媒体文件。它们包括图像、视频和音频，但也可以包括任何其他文件格式。 Blob 由“blob”词典数据类型的各个记录引用，其中包括 Blob 的内容哈希 (CID)。 {{ className: '领导' }}

Blob 文件与记录分开上传和分发。 Blob 由帐户的 PDS 实例权威存储，但视图通常由与各个应用程序（“AppViews”）关联的 CDN 提供服务，以减少 PDS 上的流量。 CDN 可以提供原始 blob 的转换（调整大小、转码等）版本。 {{ className: '领导' }}

虽然 blob 是普遍内容寻址的（通过 CID），但它们始终在个人帐户 (DID) 的上下文中被引用和管理。

空 blob（零字节）通常是有效的，尽管个别词典/应用程序可能不允许它。

## Blob 元数据

目前，Blob 唯一“受祝福的”CID 类型与存储库记录的类型类似，但使用“raw”编解码器：

- CID 版本：1 (0x01)
- 编解码器：“原始”(0x55)
- 哈希类型：`sha-256` (0x12)，大小为 256 位（0x20 字节）
- 编码：DRISL-CBOR“link”字段中的二进制序列化，以及“base32”（带有“b”前缀）用于其他地方的字符串编码

这符合 [DASL-CID](https://dasl.ing/cid.html) 规范。

示例 Blob CID，采用 Base32 字符串编码：`bafkreibjfgx2gprinfvicegelk5kosd6y2frmqpqzwqkg7usac74l3t2v4`

Blob 元数据还包括 Blob 的大小（以字节为单位）和 MIME 类型。大小和 CID 是确定性的，并且必须有效且一致。 MIME 类型在某种程度上更主观：相同的字节可能对多种 MIME 类型有效。

## Blob 生命周期

必须先将 Blob 上传到 PDS，然后才能创建引用该 Blob 的记录。请注意，服务器在接收上传时并不知道预期的 Lexicon，因此只能在初始上传时应用通用 blob 限制和限制，然后在创建记录时强制执行 Lexicon 定义的限制。

客户端在其 PDS 上使用“com.atproto.repo.uploadBlob”端点，该端点将以 Lexicon blob 对象的形式返回经过验证的元数据。客户端“应该”在上传请求上设置 HTTP“Content-Type”标头并“应该”设置“Content-Length”标头。上传也可以允许分块传输编码。服务器可以嗅探 blob mimetype 以根据声明的“Content-Type”标头进行验证，并在响应中返回修改后的 mimetype，或者拒绝上传。请参阅下面的“安全注意事项”。如果实际的 blob 上传大小与“Content-Length”标头不同，服务器应拒绝上传。

成功上传后，Blob 将被放置在临时存储中。在此状态下无法下载或分发它们。服务器应该在适当的时间跨度后“垃圾收集”（删除）未引用的临时 blob（请参阅下面的实施指南）。临时存储中的 Blob 不应包含在“listBlobs”输出中。

现在可以通过将返回的 blob 元数据包含在记录中来从记录中引用上传 blob。在处理记录创建时，服务器提取所有引用的 blob 集合，并检查它们是否已被引用或位于临时存储中。一旦记录创建成功，服务器就会使该 blob 可供公开访问。

同一存储库中的多个记录可以引用相同的 blob。重新上传已存储和引用的 Blob 不会导致现有 Blob 或记录发生任何更改。

当删除引用 blob 的记录时，服务器会检查同一存储库中是否有任何其他当前记录引用该 blob。如果不是，则该 blob 将与记录一起删除。

删除帐户后，所有托管的 blob 都会在合理的时间范围内删除。当帐户被停用、删除或暂停时，Blob 不应公开访问。

服务器可能会决定使单个 blob 无法访问，与任何帐户删除或其他帐户生命周期事件分开。

创建引用不存在的 blob 的新单独记录的创建应在创建（或更新）时被拒绝。但是，服务器可以托管引用本地不可用的 blob 的存储库记录。例如，在批量存储库导入或帐户迁移期间；数据丢失；或出于政策原因删除/删除内容。

可以使用“com.atproto.sync.getBlob”端点从 PDS 获取原始 blob。服务器应返回适当的“Content-Type”和“Content-Length” HTTP 标头。直接从 PDS 向最终用户浏览器提供媒体不是推荐或必需的模式，并且服务器不需要支持或促进此用例。有关详细信息，请参阅下面的“安全注意事项”。

## 使用和实施指南

服务器可能有自己的通用限制和 blob 策略，与 Lexicon 定义的任何约束分开。他们可能会对数据存储实施帐户范围的配额；最大斑点尺寸；内容政策；等等。任何这些限制都可能在初始上传时强制执行。服务器操作员应该意识到限制和其他限制可能会影响现有和未来应用程序的功能。为了最大限度地提高互操作性，建议运营商优先考虑对总体帐户资源消耗进行限制（例如，“总 blob 大小”配额，而不是“每个 blob”大小限制）。

某些应用程序在 Blob 上传和记录引用之间可能存在较长的延迟。为了最大限度地提高互操作性，建议服务器实现和操作员在“垃圾收集”之前留出几个小时的宽限时间，至少一小时是固定的下限。

## 安全考虑

从网络服务器提供任意用户上传的文件会引发许多内容安全问题。例如，脚本或 SVG 内容的跨站点脚本攻击 (XSS) 与其他网页形成相同的“来源”。实际上，必须为“getBlob”端点启用内容安全策略（链接：https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP）。实际上不支持直接从 Blob 存储（“getBlob”端点）动态地将资源直接提供给浏览器和 Web 应用程序。应用程序在向浏览器和 Web 代理提供服务之前，必须通过独立的 CDN、代理或其他 Web 服务来代理 blob、文件和资产，并且此类服务应实施安全预防措施。

此端点的内容安全标头的示例集是：

````
内容安全策略：default-src 'none'；沙箱
X-内容类型选项：nosniff
````

某些媒体类型可能包含敏感元数据。例如，JPEG 图像文件中的 EXIF 元数据可能包含 GPS 坐标。服务器可能会采取措施防止此类元数据的意外泄漏，例如阻止上传包含这些元数据的 blob。请参阅“未来更改”部分中的注释。

媒体文件的解析是内存安全错误和安全漏洞的一个臭名昭著的来源。甚至内容类型检测（或“嗅探”）也可能成为漏洞的来源。强烈建议服务器不要在不使用强大的沙箱机制的情况下直接解析媒体文件（图像、视频、音频或任何其他重要格式）。特别是，PDS 实例本身不应直接实现媒体大小调整或转码。

更丰富的媒体类型增加了滥用和非法内容的风险。服务部门应实施适当的机制，在检测到和报告此类内容时将其删除。

服务器可能需要采取措施防止恶意资源消耗。例如，故意耗尽磁盘空间、网络拥塞、带宽利用率等。建议进行速率限制、大小限制和配额。

## 未来可能的变化

允许的 CID 类型预计会随着时间的推移而演变。人们对较大文件类型的“blake3”很感兴趣。

应建议和/或通过 API 更改启用更具体的元数据泄漏缓解措施（例如，EXIF 元数据剥离）。提供默认安全性与始终干预操作“原始”上传的用户数据之间存在紧张关系。此外，解析和操作上传的媒体文件会引发其他类别的安全问题。
