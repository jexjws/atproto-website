#AT协议

身份验证传输协议（“AT 协议”或“atproto”）是用于构建开放社交网络应用程序的网络协议。 {{ className: '领导' }}

一些主要协议功能和设计主题包括： {{ className: 'lead' }}

- 自我验证数据和身份，允许无缝帐户迁移和内容重新分发 {{ className: 'lead' }}
- 针对“大世界”用例进行设计，扩展到数十亿个帐户 {{ className: 'lead' }}
- 应用层模式和聚合基础设施的授权 {{ className: 'lead' }}
- 重用先前 P2P 协议中的内容寻址数据模型以及网络平台 {{ className: 'lead' }} 中的网络原语

## 协议结构

**身份：**帐户控制植根于持久的 [DID](/specs/did) 标识符（如 `did:plc:ewvi7nxzyoun6zhxrhs64oiz`）。这些可以被普遍解析以确定当前服务提供商位置和与帐户关联的[加密密钥](/specs/cryptography)。 [Handles](/specs/handle) 补充了 DID，并以 DNS 主机名的形式提供可变且具有人类意义的用户名（例如“user.example.com”）。

**数据：**公共内容存储在内容寻址且可加密验证的[存储库](/specs/repository)中。数据记录和网络消息都符合统一的[数据模型](/specs/data-model)，具有[CBOR](https://en.wikipedia.org/wiki/CBOR)和JSON表示形式。 [标签](/specs/label) 是一种单独形式的轻量级元数据，单独签名并分发到存储库之外，可用于审核和标记。

**网络：** 客户端-服务器和服务器-服务器 HTTP API 使用词典模式 ([XRPC](/specs/xrpc)) 进行描述，WebSocket [事件流](/specs/event-stream) 也是如此。可以使用 [AT-URI](/specs/at-uri-scheme) 全局引用各个记录。 [个人数据服务器 (PDS)](/specs/account) 托管帐户、处理密钥管理、管理存储库、提供身份验证并代理客户端 HTTP 请求。中继从许多 PDS 主机聚合并输出统一的全网络 [firehose](/specs/sync)。

**应用程序：** 基于 atproto 构建的应用程序的 API 和记录模式在 [Lexicons](/specs/lexicon) 中指定，由 [命名空间标识符 (NSID)](/specs/nsid) 引用。应用程序特定的聚合（如搜索）由应用程序视图（App View）服务提供。客户端可以包括移动应用程序、桌面软件或 Web 界面。客户端使用[OAuth](/specs/oauth)进行授权，[权限](/specs/permission)用于授予对用户协议资源的访问权限。

AT 协议本身并没有指定常见的社交网络约定（例如关注或头像）应该如何工作，而是将它们留给应用程序设计者。应用程序通过遵循已发布的 Lexicon 模式读取和写入用户数据记录来进行互操作。

`com.atproto.*` 词典提供了通用 API，用于帐户管理和记录创建等操作。这些可以被视为 AT 协议本身的一部分，尽管它们也可以根据需要随着时间的推移进行扩展或替换。

## 协议扩展和应用

AT协议旨在在成熟的网络生态系统中提供稳定性和互操作性，同时允许产品设计人员快速提供差异化​​的功能和新颖的应用体验。

核心应用程序开发和扩展机制是在独立的 NSID 层次结构下设计和发布新的 Lexicon 模式。 Lexicon 模式可以定义新的数据记录模式、新的 HTTP API 端点和新的事件流消息类型。新应用程序通常需要新的网络聚合服务（“AppViews”）和客户端应用程序支持（例如，移动应用程序或 Web 界面）。

预计竞争的开发人员将跨组织边界重用 Lexicon 模式和公共数据记录。例如，应用程序开发人员可以重用并贡献“app.bsky.*”词典模式描述的现有公共社交图数据。他们可以通过在自己的命名空间下发布 Lexicon 模式来扩展新的数据类型。这些数据成为任何其他开发人员都可以集成和构建的公共数据公共池的一部分。

各个 Lexicon 命名空间的治理结构是灵活的。它们可以由志愿者社区、公司、财团、学术研究人员、资助的非营利组织等开发和维护。

## 缺什么？

**非公共数据：** 计划用于个人和团体数据共享的机制，并且应该支持各种应用程序功能。这些将是对协议框架的大量补充。我们建议不要使用现有协议原语简单地“附加”加密或私有内容。

**协议治理和正式标准流程：** 一旦基本协议框架被证明可以在多个互操作组织之间运行，计划将协议规范提交给现有标准机构（如 IETF）进行修订和独立审查。

各个规范文档中描述了协议未来可能的更改和扩展。
