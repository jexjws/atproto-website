# 标签

**标签** 是有关 atproto 生态系统中任何帐户或内容的元数据形式。 {{ className: '领导' }}

它们作为独立的、自我验证的数据对象存在，尽管它们也经常作为 API 响应的一部分进行分发（在这种情况下，可能不包含签名）。此外，标签“值”可以直接嵌入记录本身（“自标签”）。 {{ className: '领导' }}

标签主要由源 (DID)、主题 (URI) 和值组成。该值是一个短字符串，类似于标签或话题标签，它可能具有在标签的创建者和消费者之间共享的预定义语义。附加元数据字段可以提供附加上下文，但在任何时间点都应该只有一组连贯的元数据用于源、主题和值的组合。如果存在多组元数据，则使用“创建时间”时间戳来阐明哪个标签是当前的。 {{ className: '领导' }}

标签概念和协议原语在范围、用例和数据传输方面都很灵活。最初的设计动机之一是通过审核服务生成的标签来实现某种形式的可组合审核。但标签并不是审核专有的，并且可以在 atproto 应用程序中自由地重复用于其他目的。 {{ className: '领导' }}

核心标签模式是版本化的，本文档描述了标签版本“1”。

## 架构和数据模型

标签是协议对象，类似于存储库提交或 MST 节点。它们被规范地编码在 CBOR 的严格子集中（[DRISL](https://dasl.ing/drisl.html)）用于签名（请参阅下面的部分）。有一个代表标签的 Lexicon 定义 (`com.atproto.label.defs#label`)，但它的字段要求与核心协议对象略有不同：版本字段 (`ver`) 和签名 (`sig`) 在该版本中都是可选的。

标签对象上的字段是：

- `ver`（整数，必需）：标签模式版本。当前版本始终为“1”。
- `src`（字符串，DID格式，必填）：生成该标签的权限（账户）
- `uri`（字符串，URI 格式，必需）：此标签适用的内容。对于特定记录，“at://”URI。对于帐户，“did:”。
- `cid` （字符串，CID 格式，可选）：如果提供，则标签适用于主题 `uri` 的特定版本
- `val`（字符串，最大 128 字节，必需）：标签的值。下面讨论语义和首选语法。
- `neg`（布尔值，可选）：如果为`true`，则表示该标签“否定”具有相同`src`、`uri`和`val`的早期标签。
- `cts` （字符串，日期时间格式，必需）：标签的 `created-at` 时间戳。请注意，默认情况下，分布式系统中的时间戳不可信或不经过验证。
- `exp` （字符串，日期时间格式，可选）：此标签过期的时间戳（不再有效）
- `sig`（字节，可选）：加密签名字节。使用 [数据模型](/specs/data-model) 中的 `bytes` 类型，该类型在 JSON 中编码为采用 base64 编码的 `$bytes` 对象

当标签作为完整对象在服务之间传输时，需要“ver”和“sig”字段。

如果“neg”字段为“false”，最佳实践是根本不包含该字段。

短三字符字段名称的使用与 atproto 的大部分部分不同，并且与 JWT 更加一致。造成这种差异的动机是当网络请求和响应中包含许多标签时，尽量减少标签的大小。

## 价值

“val”字段是标签的核心。为了保持协议的灵活性，并允许本体、规范和治理结构的未来发展，这里很少指定该字符串的语义、行为和已知值。

当前的期望是标签值字符串是具有固定词汇的“标记”。它们类似于主题标签。

目前，我们强烈建议“反对”以下模式：

- 将附加结构打包到值字段中。例如，base64 编码的数据、键/值语法、值列表或数组等
- 编码任意数值（例如“分数”或“置信度”）
- 使用标点符号（如 `.`、`:`、`;`、`#`、`_`、`'`、`>` 或其他）来构建标签的命名空间
- 在值中使用 URL 或 URI
- 使用任何空白
- 使用非 ASCII 字符，包括表情符号

这些都是有前途的想法，但我们希望协调并更正式地指定这种语法扩展。

当前的一种约定是使用感叹号标点符号 (`!`) 作为系统级标签的前缀，该标签指定主题的预期行为，但不描述内容或指示行为的原因。例如，“!warn”作为一种行为，而不是“scam”作为描述性标签，后者可能会导致相同的警告行为。

围绕标签的行为、定义、含义和政策通常在其他地方传达。该值不需要完全是描述性的。

### 推荐的字符串语法

当前推荐的标签字符串语法是小写短横线语法（内部使用“-”），仅使用 ASCII 字母。具体来说：

- 小写字母 ASCII 字母（`a` 到 `z`）
- 破折号（`-`）用于内部分隔，但不作为第一个或最后一个字符
- 没有其他标点符号或空格
- 最大长度为 128 字节。越短越好（尝试将标签最多保留几十个字符），同时仍然具有一定的描述性。

## 标签生命周期：否定和过期

标签通常通过接收服务在内部广播和保留。某些服务可能会批量重新广播或重新分配标签给下游服务。他们可能会忽略并删除与其用例不相关的任何标签。他们可能会根据客户的要求“水合”标签。

在水合标签时，服务通常应仅包含“活性”和相关标签。

如果标签的权威创建者希望撤回或删除标签，他们可以通过发布具有相同来源、主题和值的新标签来实现，但将否定字段 (`neg`) 设置为 true，并使用当前时间戳（晚于任何先前的时间戳）。否定标签并不意味着该标签的反转为“真”，只是表示先前的标签已被撤回。例如，值为“spam”和“neg”为 true 的标签并不意味着该主题“不是”垃圾邮件，只是应忽略之前的“spam”标签。

遇到有效否定标签的接收服务可以在内部存储否定，并且可以重新广播否定，但不应在 API 响应中合并否定标签。

同样，可以继续保留过期标签（在过期时间戳之后），但不应继续在 API 响应中合并它们。

## 签名

标签使用公钥 [Cryptography](/specs/cryptography) 进行签名，类似于存储库提交对象。当标签在服务之间传输时，应验证签名。假设大多数最终客户端本身不会验证签名，并且可以从发送给客户端的 API 响应中删除签名以提高网络效率。客户和其他各方应该有一种机制来验证签名，通过向标签机构查询个人签名，并接收完整的标签，包括签名。

签名或验证签名的过程是构建完整版本的标签，仅使用指定的模式字段，不包括“sig”字段。这意味着包括“ver”字段，但不包括任何“$type”字段或其他可能已包含在标签的 Lexicon 表示中的未指定字段。然后，按照确定性 [DRISL](https://dasl.ing/drisl.html) 规范化规则，用 CBOR 对该数据对象进行编码。 CBOR 字节使用 SHA-256 进行哈希处理，然后使用适当的加密密钥对直接哈希字节（不是十六进制编码的字符串）进行签名（或验证）。签名字节以字节形式存储在“sig”字段中（有关表示字节的详细信息，请参阅[数据模型](/specs/data-model)）。

用于签署标签的密钥可在发行身份的 DID 文档中找到，并具有片段标识符“#atproto_label”。该密钥*可能*与用于存储库签名的“#atproto”签名密钥具有相同的值。此时，如果未找到“#atproto_label”密钥，实现“不应该”尝试使用 DID 文档中存在的其他密钥来验证签名，他们应该简单地认为签名无效并忽略标签。

### 签名生命周期

签名在收到标签时进行验证。在纳入 API 响应之前，不需要重新验证它们。

对于大型标签服务来说，签署密钥轮换可能很困难且具有破坏性。进行旋转的粗略机制是：

- 标签服务应将签名与标签一起保留，并保留用于签署标签的密钥的指示符
- 开始轮换时，暂停创建和签署新签名
- 使用新密钥更新 DID 文档
- 使用新密钥恢复签署新标签
- 在为旧标签提供查询服务时，检查用于签名的密钥。如果过期，请重新签名并保留该批次标签的签名。不应更改创建时间时间戳。
- 标签事件流回填期中较旧的标签可能具有无效签名；这是可以接受的

当遇到签名无效的标签时，一个好的做法是重新解析颁发者身份（DID 文档）并检查是否有更新的签名密钥。如果存在，应重试验证。

当上游密钥轮换发生时，下游服务可以自行决定是否批量查询并接收更新的签名；或按需获取更新的签名；或者考虑旧标签仍然有效，即使签名不再根据当前标签签名密钥进行验证。

## 记录中的自我标签

一种 Lexicon 设计模式是在记录内包含一组标签值。下游客户可以将这些解释为“自我标签”，类似于来自外部来源的标签。

请注意，存储库数据存储机制提供类似于完整标签对象的上下文和生命周期支持：

- 标签的来源是控制存储库的帐户
- 主题是记录本身，或者可能是整个存储库帐户（取决于上下文）
- CID 是记录的当前版本
- 否定和过期不是必需的，因为可以删除或更新记录以更改标签集
- 创建时间时间戳将与记录本身相同（例如，通过“createdAt”字段）
- 真实性（签名）由存储库提交签名机制提供

## 贴标服务身份

每个贴标服务都有一个服务标识，即一个 DID 文档。这是出现在标签源 (`src`) 字段中的 DID。

DID 文档还将有一个用于签名标签的密钥（ID 为“#atproto_label”；请参阅上面的签名详细信息），以及一个服务端点（ID 为“#atproto_labeler”，类型为“AtprotoLabeler”），该端点指示服务器 URL（该 URL 包括方法、主机名和可选端口，但此时没有路径段）。请注意，在现实用例中，强烈建议在默认端口 (443) 上使用 HTTPS，并且服务运营商可能会要求这样做。

根据应用程序，身份还可能有一个 atproto 存储库，其中包含“声明记录”，该记录描述了有关贴标机的特定于应用程序的上下文。这可能是与特定应用程序、客户端或 AppView 集成所必需的，但不是基础原型级别的要求。

## 标签分发端点

为贴标签服务定义了两个 Lexicon 端点来分发标签：

`com.atproto.label.subscribeLabels`：事件流 (WebSocket) 端点，用于广播新标签。实现“seq”回填机制，类似于存储库事件流，但有一些细微差别：“回填”周期可能会延长到“cursor=0”（意味着可以通过流获得标签的完整历史记录）。已编辑的标签已从流中删除原始标签，但否定仍然存在。

`com.atproto.label.queryLabels`：灵活的查询端点。可用于滚动所有标签（使用光标参数），或者可以过滤到与特定主题相关的标签。

请注意，与公共存储库内容不同，标签不*需要*是可公开枚举的。标签服务可以使用这些端点使所有标签公开可用，或者要求授权和访问控制，或者根本不实现这些端点（如果它们有另一种分发标签的机制）。

## 标签 HTTP 标头

标签通常由 atproto 服务（例如 AppViews）“混合”到 HTTP API 响应中。为了让客户端控制他们想要包含的标签源，使用了两个特殊的 HTTP 标头，这些 PDS 实现在代理请求时预计会传递：

`atproto-accept-labelers`：在请求中使用。标签服务 DID 列表，带有可选的每个 DID 标志。

`atproto-content-labelers`：用于响应。与“accept”标头相同的内容、语法和语义，但指示实际上可以查询哪些标签器。此标头中的存在并不意味着实际包含给定 DID 的任何标签，只是表示如果存在此类标签，它们就会包含在内。

这些标头的语法遵循 IETF RFC-8941（“HTTP 的结构化字段值”）第 3.1.2 节（“参数”）。值由逗号（ASCII `,` 字符）分隔，并且来自标头重复声明的值应合并到单个列表中。项目值（DID）后面可以有一个或多个可选参数，并用分号（ASCII `;` 字符）分隔。对于布尔参数，当前不支持完整的 RFC 语法（就像“param=?0”表示 false）。相反，参数的存在表示它是“true”，不存在表示它是“false”。目前不支持其他参数值类型（例如整数或字符串）。

当前唯一支持的参数是布尔参数“redact”。此标志指示服务水化标签应通过完全编辑 API 响应中的内容（而不是简单地对其进行标记）来处理特殊协议级标签值“!takedown”和“!suspend”。这可能会导致特定于应用程序的逻辑删除条目，这可能指示负责编辑的贴标者，或者可能导致内容在没有逻辑删除的情况下被删除。

这些标头的完整示例语法：

````
# 根据请求
atproto-accept-labelers：did：web：mod.example.com；redact，did：plc：abc123，did：plc：xyz789

# 关于回应：
atproto-content-labelers：did：web：mod.example.com；redact，did：plc：abc123，did：plc：xyz789
````

如果请求标头的语法无效或无法解析，则服务应返回错误而不是忽略标头。

如果贴标机 DID 在标头中重复，则应组合每个实例的参数。例如，如果 DID 与“redact”一起包含一次，一次不包含，则服务应将其视为与使用“redact”包含一次 DID 相同。 “atproto-content-labelers”响应标头应表示如何删除和解释请求标头。

如果根本未提供请求标头，则服务可以替换默认标头。这与提供没有值的标头不同，在这种情况下，服务不应添加或应用任何标签。

如果任何贴标者DID以正确的语法指示，但身份不存在；不包括 DID 文档中的贴标服务或关键条目；已在服务级别下架；或以其他方式不活跃或不起作用；那么该标签不应包含在“atproto-content-labelers”响应标头中，但也不需要被视为错误。

作为策略问题，服务实现可以决定必须满足特定条件，否则请求将出错。例如，必须包括特定贴标商 DID；或者可以包括最小或最大数量的贴标机；或者包含带有“redact”的最小或最大数量的标签。

## 安全考虑

请注意，签名不存在“域差异”，这意味着对标签进行签名存在潜在的安全风险，该标签在完全不同的上下文中也是有效对象（和签名），例如身份验证承载令牌。这使得确保正在签名的对象中不包含其他或意外的字段非常重要。
