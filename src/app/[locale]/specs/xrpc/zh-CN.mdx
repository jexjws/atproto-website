# HTTP API（XRPC）

atproto 中用于客户端-服务器和服务器-服务器请求的 HTTP API 使用一组称为“Lexicon RPC”（简称 XRPC）的通用约定。端点路径名称包含一个 [NSID](/specs/nsid)，指示指定请求和响应模式的 [Lexicon](/specs/lexicon)，通常使用 JSON 内容类型。 {{ className: '领导' }}

## 词典 HTTP 端点

HTTP 请求路径以“/xrpc/”开头，后跟 NSID。路径必须始终是顶级的，不能低于前缀。 NSID 映射到关联词典中的“id”字段。

可以在词典中表达的两种请求类型是“查询”（HTTP GET）和“过程”（HTTP POST）。遵循 HTTP REST 语义，查询 (GET) 是可缓存的，并且不应改变资源状态。过程不可缓存并且可能会改变状态。

词典“params”（在“parameters”字段下）映射到 HTTP URL 查询参数。只有某些 Lexicon 类型可以包含在 params 中，如“params”类型所指定。可以使用具有相同名称的多个查询参数来表示参数数组。当编码“boolean”参数时，应使用字符串“true”和“false”。字符串不应加引号。如果架构中包含“默认”值，则应将其包含在每个请求中以确保一致的缓存行为。

请求和响应正文内容类型可以在 Lexicon 中指定。该模式可能需要精确的 MIME 类型，或指示一系列可接受类型的 blob 模式（例如“image/*”）。

JSON 正文模式在 Lexicon 中使用常用的 atproto 数据模型指定。服务器或客户端的完全验证需要了解词典，但针对抽象数据模型的部分验证始终是可能的。

鼓励但不强制要求 CORS 支持。

### 错误响应

所有不成功的响应都应遵循标准错误响应模式。 `Content-Type` 应为 `application/json`，有效负载应为具有以下字段的 JSON 对象：

- `error` （字符串，必需）：错误的类型名称（通用 ASCII 常量，无空格）

错误类型应映射到端点的 Lexicon 架构中定义的错误名称。这使得客户端软件能够进行更具体的错误处理。特别鼓励在“400”、“500”和“502”状态代码上这样做，因为更多信息将很有用。

### Blob 上传和下载

Blob 是一种特殊情况，因为它们可以具有任何 MIME 类型，并且不直接存储在存储库中，因此不直接与 NSID 或 Lexicon 关联（尽管它们最终确实从 Lexicons 引用）。

使用 blob 的约定是客户端通过“com.atproto.repo.uploadBlob”端点上传它们，该端点返回一个“blob”JSON 对象，其中包含 CID 和有关 blob 的基本元数据。然后，客户端可以在将来的请求中包含此“blob”数据（例如，包含在新记录中）。 MIME 类型和文件大小等约束仅在第二步中进行验证。服务器可以在上传步骤中实现内容类型嗅探，并返回与提供的任何“Content-Type”标头不同的 MIME 类型，但上传 HTTP 请求中仍然需要“Content-Type”标头。

可以使用“com.atproto.sync.*” NSID 空间中的端点列出和下载特定帐户的 Blob。这些端点可以访问上传的完整原始 blob。应用程序的常见模式是通过单独的 URL（例如，在 CDN 上）镜像原始 Blob 和任何缩小的缩略图或预览版本，而不是深层链接到原始 PDS 上的“getBlob”端点。

### 光标和分页

Lexicon 设计中的一个常见模式是包含用于分页的“光标”参数。客户端不应在第一个请求中包含“cursor”参数，并应在请求之间保持所有其他参数固定。如果响应中包含游标，则可以通过在后续值中包含该值来获取下一批响应，一直持续到不再包含游标为止，表明已到达结果集末尾。

## 验证

XRPC 的主要客户端/服务器身份验证和授权方案是 OAuth，在 [Auth 规范](./oauth) 中进行了描述。

并非所有端点都需要身份验证，但还没有一致的方法来枚举哪些端点需要或不需要。

还有一种使用 HTTP Bearer 身份验证和 JWT 令牌（包括刷新令牌）的传统身份验证方案，如下所述。初始登录使用“com.atproto.server.createSession”端点，包括密码和帐户标识符（例如，句柄或注册的电子邮件地址）。这将返回一个“refreshJwt”（以及一个初始的“accessJwt”）。

大多数请求应使用访问 JWT 进行身份验证，但这些令牌的有效期很短。每隔几分钟，可以通过点击“com.atproto.server.refreshSession”端点来请求新的访问 JWT，使用刷新 JWT 而不是访问 JWT。

客户端应将令牌视为不透明字符串令牌：JWT 字段和语义不是规范的稳定部分。

生成和验证身份验证 JWT 的服务器（例如 PDS 实现）应使用“typ”标头字段实现访问令牌和刷新令牌之间的域分离：访问令牌应使用“at+jwt”，刷新令牌应使用“refresh+jwt”。请注意，`at+jwt`（在 [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) 中定义）是“访问令牌”的缩写，而不是对 atproto 中“at”的引用。

### 应用程序密码

应用密码是一种降低登录第三方客户端和 Web 应用程序时的安全风险的机制。帐户可以创建和撤销与其主密码分开的应用程序密码。它们用于以与主密码相同的方式登录，但向客户端应用程序授予稍微受限的权限，以防止帐户或身份验证设置更改（包括应用程序密码本身）等破坏性操作。

客户端和应用程序本身不需要执行任何特殊操作即可使用应用程序密码。对于大多数客户端和应用程序来说，最佳做法是在登录时包含使用应用程序密码的提醒。应用程序密码通常采用“xxxx-xxxx-xxxx-xxxx”的形式，客户端可以检查此格式以防止使用主密码意外登录（除非主密码本身具有此格式）。

### 管理员令牌（临时规范）

一些管理 XRPC 端点需要使用管理员权限进行身份验证。当前的方案是使用用户“admin”的 HTTP 基本身份验证和密码字段中的固定令牌，而不是使用 JWT 的 HTTP 承载身份验证。这意味着管理员请求除了“admin”之外没有指向客户帐户或身份的链接。

提醒一下，HTTP 基本身份验证的工作原理是将用户名和密码与冒号 (`:`) 连接在一起，并使用 `base64` （“标准”版本）对结果字符串进行编码。编码后的字符串包含在“Authorization”标头中，以“Basic”为前缀（带有分隔空格）。

例如，如果管理令牌是“secret-token”，则标头将如下所示：

```
Authorization: Basic YWRtaW46c2VjcmV0LXRva2Vu
```

本规范中需要管理员身份验证的端点集可能会过时，但目前包括：

- `com.atproto.admin.*`

### 服务间身份验证 (JWT)

本节介绍使用签名 JWT 在服务之间进行身份验证的机制。

当前的机制是使用由帐户的 atproto 签名密钥签名的短期 JWT。接收服务可以通过对照帐户的 DID 文档检查此密钥来验证签名。

JWT 参数为：

- `alg` 头字段（字符串，必需）：指示签名密钥类型（请参阅 [Cryptography](/specs/cryptography)）

发行者字段（`iss`）是发送请求的帐户的 DID。如果提供了颁发者密钥标识符（“kid”）字段，则它指示“verificationMethod”数组中帐户 DID 文档中的特定公钥，该公钥用于对令牌进行签名。密钥标识符默认为“#atproto”。请注意，“iss”是 JWT 正文字段，而“kid”是 JWT 标头字段。接收服务必须只接受特定的密钥类型（验证方法标识符），以保持注册密钥之间的安全隔离。这通常意味着仅接受“#atproto”，除非存在特定于应用程序特定或特定于服务的附加密钥类型（例如“#atproto_label”）。

<Note>
Until Spring 2026, the issuer (`iss`) could include an optional fragment identifying a service endpoint (not a public key). This syntax was not frequently used, and the specification has been changed to use `kid` instead (which identifies a public key).
</Note>

受众字段（“aud”）是请求的预期接收者的 DID 和服务端点标识符（作为片段）。如果提供了片段名称（例如“did:web:example.com#atproto_labeler”），则它对应于“service”数组中接收服务的 DID 文档中的条目。出于遗留兼容性原因，“aud”字段可能是没有服务标识符片段的裸 DID，这被解释为未定义的服务名称。接收服务必须验证受众字段是否与其自己的 DID 和服务类型相匹配，以防止重复使用或转发令牌。服务可以配置为接受“aud”中的裸 DID 以实现向后兼容性，但不需要这样做，并且未定义的服务类型与通配符不同，对“任何服务类型”也无效。

签名是使用常规 JWT 流程和帐户的签名密钥（与用于签署存储库提交的密钥相同）计算的。作为 TypeScript 伪代码，它看起来像：

```
const headerPayload = utf8ToBase64Url(jsonStringify(header)) + '.' + utf8ToBase64Url(jsonString(body))
const signature = hashAndSign(accountSigningKey, utf8Bytes(headerPayload))
const jwt = headerPayload + '.' + bytesToBase64Url(signature)
```

## 服务代理

PDS 充当客户端和其他 atproto 服务之间的通用代理。客户端可以使用 HTTP 标头来指定他们希望将请求转发到网络中的哪个服务（例如，特定的 AppView 或 Labeler 服务）。 PDS 将执行一些安全检查，然后使用由用户身份颁发和签名的服务间身份验证令牌（JWT，如上所述）转发请求。

HTTP 标头是“atproto-proxy”，值是 DID（标识服务），后跟服务端点标识符，并用“#”字符连接。 PDS 解析服务 DID，从 DID 文档中提取服务端点 URL，并将请求代理到所识别的服务器。

<Note>
Until Spring 2026, the reference PDS implementation did not pass through the full service reference to the `aud` field of the JWT auth header when proxying requests. It would strip the service endpoint identifier, and only include the bare DID.

This is in the process of being updated to include both the DID and service identifier fragment.
</Note>

用于代理标签服务的请求标头示例如下：

```
atproto-proxy: did:web:labeler.example.com#atproto_labeler
```

代理的发生必须满足一些要求。这些条件将来可能会得到扩展，以解决网络滥用问题。

- 目标服务必须具有可解析的 DID、格式正确的 DID 文档以及具有匹配标识符的相应服务条目


## HTTP 标头总结

客户端可以使用以下请求标头：

`Content-Type`：如果存在请求正文，则应包含此标头并指示内容类型。

`Authorization`：包含授权信息。有关详细信息，请参阅本规范的“身份验证”部分。

`atproto-proxy`：用于代理其他 atproto 服务。有关详细信息，请参阅本文档的“服务代理”部分。

`atproto-accept-labelers`：客户端使用它来请求来自特定标记者的标签，以将其包含并应用在响应中。详细信息请参见[标签](/specs/label) 规格。

## HTTP 状态代码摘要

`200 OK`：请求成功。如果有响应正文（可选），则应该有一个“Content-Type”标头。

`400 Bad Request`：请求无效，未被处理

`401 Unauthorized`：此端点需要身份验证。应该有一个“WWW-Authenticate”标头。

`403 Forbidden`：客户端缺乏此端点的权限

`404 Not Found`：可以指示缺少资源。这也可能表明服务器不支持 atproto，或者不支持此端点。请参阅响应错误消息（或缺少响应错误消息）来澄清。

`413 Payload Too Large`：请求正文太大。如果可能的话，分成多个较小的请求。

`429 Too Many Requests`：已超出资源限制，客户端应退出。可能存在指示特定退避时间段的“Retry-After”标头。

`500 内部服务器错误`：一般内部服务错误。客户端可以在延迟后重试。

`501 Not Implemented`：指定的端点已知，但未实现。客户端不应该重试。特别是，当服务器未实现 WebSocket 请求时返回。

“502 Bad Gateway”、“503 Service Unavailable”或“504 Gateway Timeout”：这些通常表示暂时或永久的服务停机。客户端可以在延迟后重试。

## 使用和实施指南

鼓励客户实施超时、有限重试和随机指数退避。这提高了在不可避免的偶发停机情况下的稳健性，同时最大限度地减少了陷入困境的服务器的负载。

服务器“应该”为所有带有“/xrpc/”路径前缀的请求实现自定义 JSON 错误响应，但实际上，许多服务将返回通用负载均衡器或反向代理 HTML 错误页面。客户端应对非 JSON 错误响应具有鲁棒性。

HTTP 服务器和客户端库通常会限制 URL 的整体大小，包括查询参数，这些限制限制了 XRPC 中参数的使用。

PDS 实现可以自由地限制 Blob 上传，因为它们认为合适。例如，它们可能具有全局最大大小或允许的 MIME 类型的限制集。这些应该是所有支持的词典的 blob 约束的超集。

## 安全和隐私考虑因素

在开放互联网上只能使用 HTTPS。

应注意 blob 中的个人身份信息，例如 EXIF 元数据。目前，*客户端*有责任在上传之前从 blob 中删除任何敏感的 EXIF 元数据。 PDS 也可以帮助防止意外的元数据泄漏，这也是合理的。请参阅下面的未来更改部分。

## 未来可能发生的变化

身份验证系统可能会被彻底修改。

词典应该能够指示是否需要身份验证。

PDS 作为通用网关的角色可以被形式化和扩展。可以添加用于将特定 XRPC 端点代理到其他网络服务的通用机制。可以指定查询和 blob 的通用缓存。 PDS 对第三方响应的修改可能是明确允许的。

关于是否支持 HTTP 重定向的明确决定。

当返回游标但结果列表为空以及重复游标值时，应阐明游标分页行为。

为了帮助防止意外发布嵌入媒体 blob 中的敏感元数据，可以将查询参数添加到上传 blob 端点以选择退出元数据剥离，并默认阻止上传或自动剥离所有 blob 的此类元数据。

用于服务间身份验证的“lxm”JWT 字段可能会成为必需的。
