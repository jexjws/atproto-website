# 记录按键

**记录密钥** （有时缩写为“rkey”）用于命名和引用 atproto 存储库的同一集合中的单个记录。它最终作为 AT URI 和存储库 MST 路径中的一段。 {{ className: '领导' }}

支持一些不同的记录键命名方案。每个记录 Lexicon 模式将指示应使用哪种记录键类型，具体取决于记录集合的需求和语义。 {{ className: '领导' }}

### 记录键类型：`tid`

这是最常见的记录命名方案，使用[时间戳标识符 (TID)](/specs/tid) 语法，例如“3jzfcijpj2z2a”。 TID 通常是在创建记录时从本地时钟生成的，并具有一些附加机制来确保它们始终递增并且不会与给定存储库中的相同集合一起重用或重复。

如果记录具有 TID 记录密钥，则可以推断出记录的原始创建时间戳，但请记住，这些密钥可以由最终用户指定，并且可以具有任何值，因此不应信任它们。

相同的 TID 可以用于同一存储库中不同集合中的记录。这通常表明两个记录之间的某种关系（例如，“sidecar”扩展记录）。

TID 方案的早期动机是提供松散的记录时间顺序，从而提高存储库数据结构 (MST) 的存储效率。

### 记录密钥类型：`nsid`

对于记录键必须是有效的 [NSID](/specs/nsid) 的情况。

### 记录键类型：`文字：<值>`

当集合中应该只有一条记录且具有固定的、众所周知的记录键时，使用此键类型。

最常见的值是“self”，在 Lexicon 模式中指定为“literal:self”。

### 记录键类型：`any`

任何满足整体记录键架构要求（见下文）的字符串都是允许的。这是最灵活的记录密钥类型。

这可用于对名称中的语义进行编码，例如域名、整数或（转换后的）AT URI。这可以实现重复数据删除和已知 URI 查找。

### 记录关键语法

词典字符串类型：`record-key`

无论哪种类型，记录键都必须满足一些基线语法约束：

- 仅限于 ASCII 字符的子集 — 允许的字符为字母数字 (`A-Za-z0-9`)、句点、破折号、下划线、冒号或波形符 (`.-_:~`)
- 必须至少有 1 个且最多 512 个字符
- 不允许使用特定记录键值“.”和“..”
- 必须是存储库 MST 路径字符串的允许部分（上述约束满足此条件）
- 必须允许包含在 URI 的路径组件中（遵循 RFC-3986，第 3.3 节）。  上述约束通过匹配通用 URI 路径中允许的“非保留”字符来满足此条件。

记录键区分大小写。

### 示例

有效记录键：

````
3jui7kd54zh2y
自我
example.com
~1.2-3_
dHJ1ZQ
前：修复
_
````

无效的记录键：

````
阿尔法/贝塔
。
..
# 额外
@句柄
任何空间
任意+空格
数量[3]
数量(3)
“报价”
dHJ1ZQ==
````

### 使用和实施指南

实现不应依赖 TID 的全局唯一性，也不应信任 TID 时间戳作为实际记录创建时间戳。记录密钥是“用户控制的数据”，可以由敌对帐户任意选择。

大多数处理存储库和记录的软件应该不知道记录键类型和值，并且通常将它们视为简单字符串。例如，依赖 TID 密钥将“base32”解码为唯一的“uint64”使得人们很容易依赖它用作数据库密钥，但这样做不能适应密钥格式更改，因此不鼓励这样做。

请注意，在存储库的上下文中，可以在多个集合下使用相同的记录键值。 `(did, rkey)` 的元组不是唯一的；元组“(did, collection, rkey)”是唯一的。

作为最佳实践，请尝试在几乎所有情况下将关键路径保持在 80 个字符以下。

请注意，“大多数”DID 用作记录键，但完整的 DID W3C 规范允许 DID 具有附加字符。这意味着在撰写本文时，DID 可以用作记录密钥，并且这将与当前“受祝福的”DID 方法一起使用（请注意，`did:web` 在 atproto 中仅限于完整域，而不是路径或端口规范），但这可能会在未来允许不同的 DID 方法或 DID 功能（如 `did:web` 路径）时中断。

虽然记录键区分大小写，但建议使用全小写记录键，以避免混淆并最大限度地在不区分大小写的上下文中重复使用。

### 未来可能的变化

将来可能会放宽对记录键语法的限制，以允许使用非 ASCII Unicode 字符。记录键将始终是有效的 Unicode，永远不会放宽允许任意字节字符串。

可以定义附加记录密钥类型。

最大长度可以调整。

“%”字符保留用于 URL 编码，但请注意，当前不支持此类编码。

可以添加对通用语法的附加约束。例如，需要至少一个字母数字字符。
