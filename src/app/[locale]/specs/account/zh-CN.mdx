# 账户托管

atproto 网络中的所有用户都有一个基于唯一且不可变的 DID 的“身份”。活跃用户还在个人数据服务器 (PDS) 上拥有一个“帐户”。 PDS 提供许多网络服务，包括存储库托管、授权和身份验证以及 blob 存储。帐户具有生命周期（包括帐户删除和帐户关闭）。身份可以在托管提供商之间迁移。

下游服务（包括中继和 AppView）重新分发帐户内容。每个重新分发内容的服务都独立决定要托管和重新分发的帐户和内容的范围。例如，他们可能会关注网络中的一部分帐户；制定自己的内容政策；或有区域法律义务。所有服务都应遵守某些协议级帐户操作（如下所述），例如临时帐户停用。结合起来，每个网络服务为其分发公共数据的每个帐户都有一个综合的“托管状态”。

本文档描述了帐户和身份在网络中可以具有的各种托管状态、状态更改时对下游服务的期望是什么，以及如何在托管提供商（PDS 实例）之间迁移帐户。

## 托管状态

在任何网络服务上，已知帐户在给定时间点要么是“活动”，要么不是（布尔标志）。如果帐户处于非活动状态，则服务不应重新分发该帐户的内容（存储库、个人记录、blob 等）。如果帐户未知（以前从未见过），则状态可能是未定义的。

身份元数据（DID 文档和句柄状态）以及帐户托管状态本身与托管内容不同，并且可以重新分发。

鼓励网络服务实现描述个人帐户当前托管状态的 API 端点（例如“com.atproto.sync.getRepoStatus”）。如果他们公开事件流，则当其本地帐户托管帐户状态更新时，他们还应该发出“#account”事件。

除了“active”布尔值之外，帐户还可能处于更具体的状态：

- `deleted`（active 为 false）：用户或主机已删除帐户，内容应从网络中删除。隐含永久或长期，但可能会恢复（已删除的帐户可能会在同一主机或另一主机上重新激活）。
- `deactivated`（active 为 false）：用户已暂时暂停其整个帐户。内容不应显示或重新分发，但不需要从基础设施中删除。暗示有时间限制。也是迁移到另一个 PDS 实例后帐户的初始状态。
- `takendown`（active 为 false）：主机或服务已删除帐户。暗示永久或长期，但可能会恢复。
- `暂停`（active 为 false）：主机或服务已暂时暂停帐户。暗示有时间限制。
- `desynchronized`（活动可能为 true）：主机或服务检测到同步帐户存储库时出现问题，并且可能丢失内容
-“throttled”（活动可能为 true）：主机或服务已暂停处理新内容，因为已超出资源速率限制

将来可能会添加新的帐户状态。为了防止破坏预期，相关 API 端点（例如“com.atproto.sync.getRepoStatus”和“com.atproto.sync.subscribeRepos”事件流上的“#account”事件）包含“active”作为布尔标志，以及指示特定状态的附加“status”字符串。服务应使用“active”标志来控制总体帐户可见性（可观察的行为），并使用“status”字符串作为澄清，这可能确定更具体的基础设施行为（例如数据删除）或帮助理解行为（例如超出速率限制）。

停用和暂停状态被暗示是暂时的，尽管它们可能具有不确定的时间段。删除和删除意味着更为最终，但在技术上仍然可以恢复（并且在实践中经常如此）。

下游服务可能会决定在删除（例如删除）后快速删除内容，或者干脆停止重新分发内容，直到稍后。

身份也可能被墓碑化，这也意味着是永久和最终的，但在技术上可以在某些情况下逆转。如果帐户的身份为“逻辑删除”，则帐户托管状态应解释为“已删除”。

总而言之，当帐户状态为非“活动”时，不应重新分发的内容包括：

- 存储库导出（CAR 文件）
- 回购记录
- 转换记录（“视图”、嵌入等）
- 斑点
- 转换后的斑点（缩略图等）

### 托管状态传播

与 atproto 的其他方面不同，帐户状态不是自我认证的，并且没有在任意方之间进行身份验证转移或重新分配帐户状态的方法。

最常见的是，帐户状态“逐跳”传播，每个“下游”服务接受并采用上游帐户的托管状态。如果中间服务（例如中继）覆盖其上游的状态（例如，基础设施帐户删除），它们将向下游广播并传播该操作给订阅者。

默认情况下，如果帐户当前的活动 PDS 不可用，则帐户状态应保持不变，至少在一段时间内如此。这可以在基础设施临时中断期间保持网络弹性和帐户在线。服务可能会为其 PDS 主机长时间保持离线状态的帐户决定自己的策略。

一般期望是，如果帐户在上游服务中处于非活动状态，下游服务不会将其列为“活动”。然而，“上游”的概念是非正式的，服务可能需要针对某些极端情况定义自己的策略。例如，AppView 可能会使用多个独立的中继提供商，由于策略差异，这些提供商会报告同一帐户的不同状态。如果中继和 PDS 之间的网络连接中断，它们可能会报告同一帐户的不同状态。

如果对帐户在网络中的一般状态有疑问，可以使用“com.atproto.sync.getRepoStatus”端点查询该帐户当前活动的 PDS 主机。如果帐户在那里不是“活跃”的，那么通常预计它在其他地方也不会活跃，特别是在用户发起的操作（停用或删除）的情况下。

### 内容删除

与整体帐户状态分开，个别内容可能会被删除。当帐户从其公共存储库中删除记录时，托管服务应删除对该内容的公共访问权限。

受益于显式“墓碑”（指示内容以前存在）的应用程序应该显式地将它们设计到 Lexicon 模式中。在没有明确的应用程序级逻辑删除的情况下，服务不应区分从未存在的内容和已完全删除的内容。请注意，这与确认帐户级删除不同，后者是鼓励的。

## PDS 帐户迁移

在较高级别上，帐户的当前 PDS 主机在帐户的 DID 文档中指示。如果 DID 文档更新为指向新的 PDS 主机，该主机上的帐户状态为“活动”，并且有一个正在运行的存储库（具有有效的签名和提交“rev”），则该帐户已有效迁移。

在协议级别，这就是帐户迁移的工作原理。在某些情况下，当任何先前的 PDS 实例不可用或具有非活动帐户状态时，进入上述状态可能是唯一可用的帐户恢复路径。

然而，在常见情况下，当当前功能良好的 PDS 上存在活动帐户时，可以实现更加无缝的帐户迁移过程。它可以概括为几个高级步骤：

- 在新的 PDS 上创建帐户（可能以“active” false 开头，例如“deactivated”）
- 将数据从旧 PDS 迁移到新 PDS
- 更新身份（DID 文档）以指向新的 PDS 并使用新的 atproto 签名密钥。对于 PLC DID，通常还涉及更新 PLC 旋转密钥。这会导致至少从新 PDS 主机发出“#identity”事件，最好也从旧 PDS 发出。
- 更新两个 PDS 实例上的帐户状态，例如旧的处于非活动状态，而新的处于活动状态。这会导致每个 PDS 发出“#account”事件。
- 从新的 PDS 发出“#sync”和/或“#commit”事件，由新的 atproto 签名密钥签名，具有更高的提交“rev”。

## 安全考虑

帐户托管状态未经身份验证，并且特定于每个单独的网络服务。当前活动的 PDS 主机是查询总体帐户状态的良好默认值，尽管它可能不代表广泛的网络共识（例如，中间删除），并且 PDS 主机在技术上可能会歪曲帐户激活状态。

对于下游服务来说，处理帐户状态更改可能会占用大量资源。建议在帐户 (DID) 级别和上游服务提供商（例如 PDS）级别进行速率限制，以防止不良行为者发起资源耗尽攻击。在这种情况下，将相关帐户置于非活动状态（例如“暂停”）可能是适当的，以防止帐户被“锁定打开”。

身份控制（DID 和句柄）在 atproto 权限模型中至关重要。当用户将其身份管理委托给该主机时（例如，使用“did:plc”时），用户应特别注意选择和评估其 PDS 主机。
