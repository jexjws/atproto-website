# 句柄

DID 是 atproto 中帐户的长期持久标识符，但它们可能不透明且不适合人类使用。 **句柄** 是可变且人性化的帐户用户名，采用 DNS 主机名的形式。例如，“user.example.com”。句柄必须双向链接到 DID：DID 文档必须声明句柄，并且句柄必须解析为 DID 标识符。支持两种解析 DID 句柄的方法：一种使用 TXT DNS 记录，另一种使用 HTTPS `/.well-known/` URL 路径。 {{ className: '领导' }}

“主机名”的定义（作为所有可能的“DNS 名称”的子集）随着时间的推移并在多个 IETF RFC 中不断演变。一些相关文档是 [RFC-1035](https://www.rfc-editor.org/rfc/rfc1035)、[RFC-3696](https://www.rfc-editor.org/rfc/rfc3696) 第 2 部分和 [RFC-3986](https://www.rfc-editor.org/rfc/rfc3986) 部分3. 几乎每个有效的“主机名”也是有效的句柄，但也有少数例外（如下所述）。 {{ className: '领导' }}

## 句柄标识符语法

词典字符串格式类型：`handle`

综合其他标准，并具体定义“handle”语法：

- 整个句柄必须仅包含 ASCII 字符，并且最多可以有 253 个字符长（实际上，句柄可能会被限制为稍短的长度）
- 整个句柄分为多个段（在标准文档中称为“标签”），用 ASCII 句点 (`.`) 分隔
- 不允许有前导或尾随 ASCII 句点，并且必须至少有两个段。也就是说，不允许“裸”顶级域作为句柄，即使有效的“主机名”和“DNS 名称”也是如此。 DNS 名称的“尾随点”语法不允许用于句柄。
- 每个段必须至少有 1 个、最多 63 个字符（不包括句点）。允许的字符为 ASCII 字母 (`a-z`)、数字 (`0-9`) 和连字符 (`-`)。
- 分段不能以连字符开头或结尾
- 最后一段（“顶级域”）不能以数字开头
- 句柄不区分大小写，应标准化为小写（即将 ASCII `A-Z` 标准化为 `a-z`）

明确地说（上述规则已经指定了这一点），句柄中不允许有空格、空字节、连接字符或其他 ASCII 控制字符，包括作为前缀/后缀。

现代“主机名”（以及句柄）允许在大多数位置使用 ASCII 数字，但最后一段（顶级域，TLD）不能以数字开头。

IP 地址不是有效的语法：IPv4 地址的最后一段以数字开头，而 IPv6 地址则用冒号 (`:`) 分隔。

句柄语法的参考正则表达式 (regex) 为：

````
/^([a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?\.)+[a-zA-Z]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?$/
````

## 其他非语法限制

“保留”顶级域不应无法通过语法验证（例如，在 atproto Lexicon 验证中），但它们必须立即使任何注册、解析等尝试失败。另请参阅：[https://en.wikipedia.org/wiki/Top-level_domain#Reserved_domains](https://en.wikipedia.org/wiki/Top-level_domain#Reserved_domains)

atproto 中不应使用“.local”主机名（用于本地网络上的 mDNS）。

“.onion” TLD 是 Tor 协议隐藏服务的特例。通过 Tor 解析句柄需要整个生态系统的支持，因此目前不允许这样做。

综上所述，禁用 TLD 的初始列表包括：

- `.alt`
- `.arpa`
- `.example`
- `.内部`
- `.无效`
- `.local`
- `.localhost`
- `.onion`

“.test” TLD 用于示例、测试和开发。它可以用于 atproto 开发，但在现实环境中应该会失败。

“.invalid” TLD 只能用于特殊的“handle.invalid”值（见下文）。该值在 Lexicon 模式语言中在语法上是有效的，但在大多数上下文中不应被接受为有效句柄。

## 标识符示例

语法上有效的句柄（可能有也可能没有现有 TLD）：

````
jay.bsky.social

name.t--t // 不是真正的 TLD，但语法正确
XX.LCS.MIT.EDU
a.co
xn--notarealidn.com
xn--fiqa61au8b7zsevnm8ak20mc4a87e.xn--fiqs8s
xn--ls8h.test

````

无效语法：

````
jo@hn.test
💩.测试
约翰..测试
xn--bcher-.tld
约翰.0
cn.8
www.masełkowski.pl.com

````

````
2gzyxa5ihm7nsggfxnu52rck2vv4rvmdlkiu3zzui5du4xyclen53wid.onion
笔记本电脑本地

````

## 处理分辨率

句柄在 atproto 中的作用有限，几乎在所有情况下都需要解析为 DID。解析机制必须在某个时间点表现出对域名的合理程度的权威，并且需要相对有效地查找。目前支持两种解析机制：一种使用包含 DID 的 TXT DNS 记录，另一种通过 HTTPS 访问特殊的“/.well-known/” URL。

客户端可以依赖网络服务（例如，他们的 PDS）使用“com.atproto.identity.resolveHandle”端点来解析它们的句柄，并且通常不需要自己直接实现解析。

DNS TXT 方法是单个句柄配置的推荐和首选解析方法，但服务应完全支持这两种方法。 HTTPS 方法的预期用例是现有的大型 Web 服务，这些服务可能没有自动注册数千或数百万条 DNS TXT 记录的基础设施。

在 DID 也被解析并且当前 DID 文档被确认链接回句柄之前，句柄不应被信任或被视为有效。句柄和 DID 之间的链接必须双向确认，否则任何人都可以为第三方帐户创建句柄别名。

### DNS TXT 方法

对于此解析方法，会在句柄主机名下为“_atproto”子域注册 DNS TXT 记录。记录值应具有前缀“did=”，后跟完整的 DID。此方法与 [RFC-1464](https://www.rfc-editor.org/rfc/rfc1464.html)“使用域名系统存储任意字符串属性”一致。

例如，句柄“user.example.com”将在名称“_atproto.user.example.com”上有一条 TXT 记录，并且该值将类似于“did=did:plc:ewvi7nxzyoun6zhxrhs64oiz”。

任何值不以“did=”开头的 TXT 记录都应被忽略。在任何时间点都应该只存在一条有效记录。如果存在多个具有不同 DID 的有效记录，解析将失败。在这种情况下，可以在延迟后重新尝试解析，或者使用递归解析器。

请注意，如果附加的“_atproto.”名称段使整个名称超过 DNS 查询的最大字符数 253 个，则无法使用此方法解析非常长的句柄。 HTTPS 方法适用于此类句柄。

不需要 DNSSEC。

### HTTPS 众所周知的方法

对于这种解析方法，句柄域的 Web 服务器在路径“/.well-known/atproto-did”处实现了一个特殊的众所周知的端点。有效的 HTTP 响应将具有 HTTP 成功状态 (2xx)、“Content-Type”标头设置为“text/plain”，并包含 DID 作为 HTTP 正文，没有前缀或包装格式。

例如，句柄“user.example.app”将通过对“https://user.example.app/.well-known/atproto-did”的 GET 请求进行解析，有效的响应如下所示：

````
HTTP/1.1 200 好
内容长度：33
内容类型：文本/纯文本
日期：2023 年 6 月 14 日星期三 00:47:21 GMT

did:plc:ewvi7nxzyoun6zhxrhs64oiz
````

响应“Content-Type”标头不需要严格验证。

Web 服务器的响应正文不应包含任何前缀或后缀空格，但客户端应在尝试解析为 DID 之前从响应正文中删除少量前缀或后缀空格。

所有实际句柄解析都需要默认端口 (443) 上的安全 HTTPS。不安全的HTTP只能用于本地开发和测试。

允许 HTTP 重定向（例如 301、302），最多可达到合理的重定向跳数。

### 无效句柄

如果确认已知 DID 的句柄不再解析，则应将其标记为无效。在 API 响应中，特殊句柄值“handle.invalid”可用于指示给定 DID 没有双向有效句柄。大多数情况下（搜索查询、API 请求等）无法使用此句柄。

### 解决方案最佳实践

可以并行尝试两种解决方法，并使用第一个可用的成功结果。如果两种方法返回冲突的结果（也称为不同的 DID），则应首选 DNS TXT 结果，但也可以将结果记录为不明确并稍后重试。

服务在内部缓存句柄解析结果被认为是最佳实践，直到某个生命周期，并定期重新解析。 DNS TTL 值提供了可能的缓存生命周期，但对于句柄解析用例来说可能过于激进（也称为生命周期太短）。

使用递归 DNS 解析器可以帮助解决传播延迟问题，这对于帐户更改其句柄并等待确认的用例非常重要。

使用这两种技术，从相对可信的网络环境和配置发起解析请求是有益的。从多个区域和环境运行解决请求可以帮助减轻（尽管不能完全解决）对流量操纵或故意分段响应的担忧。

## 使用和实施指南

在用户界面中，句柄可以以“at”符号为前缀（例如“@user.example.com”），但这对于记录、API 和其他后端上下文中的句柄来说不是有效的语法。

国际化域名（“IDN”或“punycode”）与低级句柄语法不直接相关。在其编码形式中，IDN 已经是有效的主机名，因此也是有效的句柄。此类句柄必须以编码的 ASCII 形式存储和传输。 “看起来像”IDN 但不解析为有效 IDN 的句柄是有效句柄，就像它们是有效主机名一样。应用程序可以选择将 IDN 句柄解析并显示为 Unicode。

句柄不区分大小写，这意味着它们可以安全地从用户输入标准化为小写 (ASCII) 形式。只有标准化（小写）句柄才应存储在记录中或在出站 API 调用中使用。应用程序不应保留用户提供的大小写信息并尝试以小写以外的任何形式显示句柄。例如，句柄输入字符串“BlueskyWeb.xyz”应标准化、存储并显示为“blueskyweb.xyz”。长的全小写句柄可能会对可读性和可访问性造成挑战。子域分隔（句点）、连字符或在应用程序协议中使用“显示名称”都会有所帮助。

众所周知，很长的句柄会给用户界面带来挑战，但协议中允许使用它们，并且应用程序开发人员应该支持它们。

看起来类似于知名域的句柄会带来安全和模拟挑战。例如，“paypa1.com”或“paypal.cc”等句柄会与“paypal.com”混淆。很长的句柄在开头或结尾被截断时可能会导致类似的问题（“paypal.com…”）。

通常不应根据本地上下文截断句柄。例如，句柄“@alice.example.com”不应显示为“@alice”，即使在“example.com”服务的本地上下文中也是如此。

句柄“命名空间”（例如，作为注册域上的子域）的提供者可以对他们希望的句柄施加任何附加限制。建议将允许的段长度限制在合理的范围内，并保留一组通用的段字符串，如“www”、“admin”、“mail”等。有多个“通常不允许的用户名”的公共列表可以用作起点。

从实际角度来看，句柄应限制为最多 244 个字符，少于 DNS 名称允许的 253 个字符。这是因为 DNS 验证使用前缀“_atproto.”，它添加了 9 个字符，并且整个名称需要有效。

处理主机名预计是主流 DNS 域名，通过主流 DNS 名称系统注册。使用非标准 TLD 或使用非标准命名系统的句柄将无法与 atproto 生态系统中的其他网络服务和协议实现进行互操作。

如果无法再验证帐户的句柄（也称为“handle.invalid”情况），托管帐户的 PDS 实现*可能*会防止存储库突变。其他网络服务通常应继续显示内容（以防止损坏），可能带有上下文注释或警告指示符。

互操作测试向量可从 [atproto-interop-tests](https://github.com/bluesky-social/atproto-interop-tests) 存储库中获取。
