# 事件流

除了常规的 [HTTP API](/specs/xrpc) 端点之外，atproto 还支持连续事件流。消息模式和端点名称与传输无关，并在 [Lexicons](/specs/lexicon) 中定义。初始编码和传输方案在 [WebSockets](https://en.wikipedia.org/wiki/WebSocket) 上使用二进制 [DRISL-CBOR 编码](/specs/data-model)。 {{ className: '领导' }}

流的词典类型是“订阅”。该模式包括端点的标识符（“id”）、“消息”模式（联合，允许多种消息类型）和错误类型列表（“错误”）。

客户端通过在指定端点启动 WebSocket 连接来订阅特定流。流目前是单向的，消息从服务器流向客户端。客户端可以在打开连接时提供查询参数来配置流。

**回填窗口**机制允许客户端赶上他们可能错过的流消息。在较高级别上，这是通过为流事件分配单调递增的序列号，并允许客户端在启动连接时指定初始序列号来实现的。该机制的目的是确保在合理的时间窗口（例如，几小时或几天）内发生中断后事件的可靠传递。它并不是让客户端能够一直回滚到流的开头。

`com.atproto` 命名空间中的所有初始订阅词典都使用回填机制。然而，流不需要回填机制（甚至是我们在下面定义的游标）。不需要可靠传递的订阅端点不需要实现回填机制或使用序列号。

初始订阅端点也是公共的，不需要身份验证或事先许可即可订阅（尽管可能会对客户端施加资源限制）。但订阅端点可能需要在连接时使用现有的 HTTP API (XRPC) 身份验证方法进行身份验证。

## 流媒体协议 (v0)

总而言之，消息被编码为 [DRISL-CBOR](https://dasl.ing/drisl.html) 并通过二进制 WebSocket 发送。客户端使用查询参数连接到特定的 HTTP 端点，然后升级到 WebSocket。每个 WebSocket 帧都包含两个 CBOR 对象，其中字节连接在一起：标头（指示消息类型）和实际消息。

WebSockets“生活标准”目前由 [WHATWG](https://en.wikipedia.org/wiki/WHATWG) 维护，可以在 [https://websockets.spec.whatwg.org/](https://websockets.spec.whatwg.org/) 上找到完整内容。

＃＃＃ 联系

客户端通过打开 HTTP 连接并升级到 WebSocket 来初始化流订阅。默认端口 (443) 上的 HTTPS 和“WebSocket Secure”(`wss://`) 应用于 Internet 上的所有连接。 HTTP、明文 WebSocket (`ws://`) 和非标准端口只能用于测试、开发和本地连接（例如，在实现 SSL 的反向代理后面）。从客户端的角度来看，未能升级到 WebSocket 的连接是一个错误。

可以在初始 HTTP 请求中提供查询参数，以按照端点的 Lexicon 模式中指定的特定于应用程序的方式配置流。

错误通常通过流本身返回。连接时错误作为流上的第一条消息发送，然后服务器断开连接。但有些错误无法通过流处理，而是作为 HTTP 错误返回：

- `405 Method Not allowed`：针对流端点的非 GET HTTP 请求返回给客户端。
-“426 需要升级”：如果对流端点的请求中未包含“升级”标头，则返回给客户端。
- `429 Too Many Requests`：经常用于速率限制。客户端可以在延迟后重试。鼓励支持“Retry-After”标头。
- `500 Internal Server Error`：客户端可能会在延迟后重试
- `501 Not Implemented`：服务未实现 WebSocket 或流，至少对于此端点而言。客户端不应重试。
- `502 Bad Gateway`、`503 Service Unavailable`、`504 Gateway Timeout`：客户端可能会在延迟后重试

服务器“应该”以 JSON 形式返回 HTTP 主体，并带有这些状态代码的标准 XRPC 错误消息架构。但客户端还需要对意外的响应正文格式具有鲁棒性。常见情况是在计划或计划外停机期间收到默认负载平衡器或反向代理错误页面。

如果一段时间内没有消息，服务器或客户端可能会决定断开开放流连接。无限期地保持连接打开也是可以接受的。

### 框架

每个二进制 WebSocket 帧包含两个串联的 DRISL-CBOR 对象。第一个是 **标头**，第二个是 **有效负载。**

标头 CBOR 对象具有以下字段：

- `op`（“操作”，整数，必需）：固定值，表示此帧包含的内容
    - `1`：一条常规消息，类型用`t`表示
    - `-1`：错误消息
- `t`（“type”，字符串，可选）：如果“op”为“1”，则为必需，以简短形式指示此消息的 Lexicon 子类型。不包含完整的 Lexicon 标识符，仅包含一个片段。例如：`#commit`。如果“op”为“-1”，则不应包含在标头中。

客户端应忽略带有未知“op”或“t”值的标头的帧。应忽略标头和有效负载中的未知字段。无效的成帧或 DRISL-CBOR 编码是硬错误，客户端应该丢弃整个连接而不是跳过帧。服务器应该忽略从客户端收到的任何帧，而不是将它们视为错误。

错误负载均具有以下字段：

- `error` （字符串，必需）：错误类型名称，没有命名空间或 `#` 前缀
- `message` （字符串，可选）：错误的描述

发送或接收错误帧后应立即关闭流。

消息有效负载必须始终是对象。他们应该省略“$type”字段，因为该信息已在标头中指示。 atproto 中的 WebSocket 帧的大小没有具体限制，但它们应该保持相当小（大约几兆字节）。

如果客户端无法跟上消息的速率，服务器可能会发送“太慢”错误并关闭连接。

### 序列号

流可以选择使用每个消息的序列号来提高传输的可靠性。客户端会跟踪他们收到并成功处理的最后一个序列号，并且可以在重新连接后指定该序列号以接收任何丢失的消息，直到某个回滚窗口。服务器在连接之间不保留客户端状态。语义类似于 [Apache Kafka](https://en.wikipedia.org/wiki/Apache_Kafka) 的消费者组和其他流处理协议。

订阅词典必须包含“seq”字段（整数类型）和“cursor”查询参数（整数类型）。并非所有消息类型都需要包含“seq”。错误不会，并且通常会出现不持久的“#info”消息类型。

序列号始终是正整数（非零），并且单调递增，但在其他方面具有灵活的语义。它们可能包含任意间隙。例如，它们可能是时间戳。

为了防止在使用 Javascript 时出现混淆（默认情况下将所有数字表示为浮点数），序列号应限制在可以安全地由 64 位浮点数表示的整数范围内。即，整数范围“1”到“2^53”（不包括上限）。

游标和序列号的连接时间规则：

- 未指定“光标”：服务器从当前流位置开始传输
- `cursor` 高于当前的 `seq` （“将来”）：服务器发送错误消息并关闭连接
- `cursor` 位于回滚窗口中：服务器发送任何具有大于或等于 `seq` 编号的持久消息，然后在“赶上”当前流后继续
- `cursor` 比回滚窗口旧：流中的第一条消息是指示 `cursor` 太旧的信息，然后从最旧的可用 `seq` 开始并发送整个回滚窗口，然后继续当前流
-“cursor”为“0”：服务器将从最旧的可用“seq”启动，发送整个回滚窗口，然后继续当前流

序列号的范围是服务提供者（主机名）和端点（NSID）的组合。这大致对应于用于连接的“wss://” URL。也就是说，序列号在同一服务的不同流端点之间可能是唯一的，也可能不是唯一的。

服务应确保序列号不被重复使用，通常是通过在通过流传输事件之前将事件（带有序列号）提交到稳健的持久存储中。

在某些灾难性故障模式（或基础设施发生重大变化）中，服务器可能会丢失回填窗口中的数据，并且需要将序列号重置回“1”。在这种情况下，如果客户端重新连接更大的数字，服务器将向客户端发回“FutureCursor”错误。客户需要决定在这些情况下采取什么策略。我们建议客户端将无序或重复的序列号视为错误，不处理消息并断开连接。大多数客户端不应在没有人工操作员干预的情况下重置序列状态，尽管对于某些不需要可靠传递流中每个事件的临时客户端来说，这可能是合理的行为。

## 使用和实施指南

当前的流传输主要是为服务器到服务器的数据同步而设计的。 Web 应用程序也可以直接从最终用户浏览器进行连接，但请注意，解码二进制帧和 DRISL-CBOR 并非易事。

WebSocket 客户端库并不始终支持 HTTP 重定向和 WebSocket 升级的组合。 atproto 中没有特别要求或禁止支持。

atproto 未指定支持的 WebSockets 标准版本。当前稳定的 WebSocket 标准是版本 13。实现应做出合理的努力来支持现代版本，并具有一定的向后兼容性。

WebSocket 具有明显的资源速率限制和拒绝服务问题。建议对服务器和客户端进行网络带宽限制和限制。服务器应该调整并发连接限制和缓冲区大小以防止资源耗尽。

如果服务需要重置序列状态，建议选择一个新的初始序列号，该序列号的余量高于任何先前的序列号。例如，在持久存储丢失之后，或者清除先前的流状态。

引用特定主机上的流端点的 URL 通常应使用“wss://”作为 URI 方案（而不是“https://”）。

## 安全和隐私考虑

如“连接”部分中所述，仅应使用“wss://”(SSL) 进行互联网上的流连接。公共服务应拒绝非 SSL 连接。

大多数 HTTP XRPC 端点使用 JSON 形式的内容，而流端点直接使用 CBOR 对象作为不受信任的输入。必须采取预防措施来防止恶意数据编码和数据结构操纵。具体问题在[数据模型](/specs/data-model) 和[存储库](/specs/repository) 规范中讨论。

## 未来可能的变化

可以调整序列号方案以更好地支持分片流。其动机是通过跨多个连接来处理公共互联网上更高的数据吞吐量。

可以指定附加传输（WebSocket 除外）和编码（CBOR 除外）。例如，文本 WebSocket 帧中的 JSON 有效负载在浏览器中解码起来会更简单。

可以采用其他 WebSocket 功能：

- 传输压缩“扩展”，例如“permessage-deflate”
- 子协议的定义
- 双向消息传递
- 1000级响应代码

本规范中的歧义可能会得到解决，或保持开放状态。例如：

- HTTP 重定向
- CORS 和浏览器连接的其他问题
- 最大消息/帧大小

可以支持身份验证方案，类似于常规 HTTP XRPC 端点的身份验证方案。
