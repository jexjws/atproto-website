# 数据同步

独立网络参与者之间公共数据的同步是atproto（以“Authenticated Transfer”命名）的定义特征之一。大规模数据重新分配是值得信赖的、低延迟的和资源高效的。 {{ className: '领导' }}

atproto中主要有两种数据同步机制。通过 HTTP 将完整存储库导出为 CAR 文件，支持批量数据传输。实时同步可以通过存储库事件流（通过 WebSocket）提供，通常称为“消防水带”。它们一起使用，可以实现完整、实时更新且经过身份验证的网络数据副本。 {{ className: '领导' }}

## 存储库修订

如 [存储库规范](/specs/repository) 中所述，对存储库的每次提交都有一个 *revision* 值，编码为 [TID](/specs/tid) 字符串。修订版充当逻辑时钟来跟踪各个存储库的同步状态。即使帐户在主机之间迁移或长时间处于不活动状态，修订版本也必须始终在同一存储库的提交之间增加。为了简化修订管理，PDS 实现应使用当前挂起时间（转换为 TID）作为每次提交的修订。使用挂机时间时，检查新版本是否高于先前版本仍然很重要，以考虑时钟漂移或并发更新。

同步服务应拒绝或忽略具有与未来时间戳（超出短模糊时间漂移窗口）相对应的修订值的存储库更新。服务可以跟踪他们所看到的每个帐户的提交修订，并使用它来验证同步状态。

向服务发出 API 请求的客户端可能想知道该服务是否已将最近的更新同步并索引到经过身份验证的帐户的存储库。例如，如果客户更新其帐户的个人资料记录（通过写入 PDS），然后立即从单独的服务请求其个人资料的更新视图，则客户会想知道是否应用了记录更新。服务可以使用“Atproto-Repo-Rev”HTTP 响应标头指示同步状态，该响应标头应包含发出 API 请求的帐户的单个提交修订版 (TID)。

## 存储库导出

可以使用“com.atproto.sync.getRepo”XRPC 端点 (HTTP GET) 从帐户的 PDS 主机获取完整存储库导出。该端点未经身份验证，并返回所有存储库记录、MST 节点和当前签名的提交对象，所有这些都在单个 CAR 文件中。

其他服务器可能提供完整存储库 CAR 文件的缓存或镜像副本。对于此类镜像来说，及时（几秒或几分钟内）遵守存储库更新（例如，记录删除）和帐户状态更改（例如，帐户停用或删除）非常重要。这通常意味着静态存储库快照不应以批量形式公开重新分发（例如，存档数据集或 torrent 文件）。

## 存储库事件流

存储库事件流（“firehose”）提供有关存储库状态（“#commit”和“#sync”事件）、DID 文档和句柄（“#identity”事件）以及帐户托管状态（“#account”事件）更改的实时更新。有线格式是带有 CBOR 编码消息和基于序列的恢复游标的 WebSocket，如 [事件流规范](/specs/event-stream) 中所述。

多个网络服务在同一“com.atproto.sync.subscribeRepos”流端点下提供 Firehose 端点，并具有兼容的消息类型和语义。 PDS 主机提供了一个消防管道，其中包括所有托管帐户的更新。 **中继** 是订阅多个上游消防软管（例如，多个PDS主机）并将它们聚合到单个组合事件流中的网络服务。尝试聚合网络中所有 PDS 实例的帐户的中继会输出“全网络”消防水带。

通过 Firehose 同步的存储库数据是自我认证的，并包含可验证的签名。使用服务可以验证同步数据，而无需向帐户的 PDS 主机发出额外请求。单个存储库的缺失更新可以通过“#commit”消息流中的间隙来检测。但是，如果中间服务要过滤与存储库相关的所有消息，则消费服务不一定能够检测到这一点。

身份和帐户信息“不”是自我认证的，消费服务负责验证它。这通常意味着独立的[DID分辨率](/specs/did)和[句柄分辨率](/specs/handle)。 [帐户托管状态](/specs/account) 可以根据帐户的 PDS 主机进行检查，尽管中间服务应用删除是合法的。

事件消息类型在下面指定，并且也在`com.atproto.sync.subscribeRepos`词典模式中声明。所有事件类型的一些字段都是相同的：

- `seq`（整数，必需）：用于确保可靠消费，如事件流中所述
- `did` （具有 DID 语法的字符串，必需）：与事件关联的帐户。 `#commit`消息不一致，使用`repo`作为字段名
- `time`（具有日期时间语法的字符串，必需）：接收事件时间的非正式且非权威的估计。中介服务可能决定按原样传递此字段，或更新到当前时间

Firehose 事件流消息的最大大小硬性限制为 5 MB（以 WebSocket 帧测量）。这包括所有编码和嵌套开销，并排除了一些不会超出词典模式限制的消息。通常预计消息远低于此硬性大小限制。此限制可能会随着时间的推移而变化。

### `#identity` 事件

表示所指示的身份（即 DID 文档或句柄）*可能*已发生更改，并且可以选择当前句柄是什么。不表明发生了什么变化，或可靠地表明身份的当前状态是什么。

事件字段：

- `seq`（整数，必需）：对于所有事件类型都相同
- `did` （具有 DID 语法的字符串，必需）：对于所有事件类型都相同
- `time` （具有日期时间语法的字符串，必需）：对于所有事件类型都相同
- `handle` （带有句柄语法的字符串，可选）：此标识的当前句柄。如果句柄当前未正确解析，则可能为“handle.invalid”。

“handle”字段存在或不存在并不表示句柄已更改。

语义和预期行为是下游服务应更新指定 DID 的任何缓存身份元数据（包括 DID 文档和句柄）。他们可能会将缓存标记为过时，立即清除缓存的数据，或尝试重新解析元数据。

身份事件是在“尽力而为”的基础上发出的。 DID 文档或句柄解析状态可能会在没有任何 atproto 服务检测到更改的情况下发生更改，在这种情况下，不会发出事件。当实际上没有任何改变时，事件也可能被冗余地发出。

中介服务（例如中继）可以选择修改或传递身份事件：

- 他们可以用自己的决议结果替换句柄；或者始终删除句柄字段；或者总是不加改变地传递它
- 如果他们观察到身份实际上没有改变，他们可能会过滤掉身份事件
- 他们可能会根据他们独立意识到的变化发出身份事件（例如，通过定期重新验证句柄）

### `#account` 事件

指示发出事件的服务的 [帐户托管状态](/specs/account) 可能发生变化，以及新状态是什么。例如，它可能是创建、删除或临时暂停帐户的结果。该事件描述了当前的托管状态，而不是发生了什么变化。

事件字段：

- `seq`（整数，必需）：对于所有事件类型都相同
- `did` （具有 DID 语法的字符串，必需）：对于所有事件类型都相同
- `time` （具有日期时间语法的字符串，必需）：对于所有事件类型都相同
- `active`（布尔值，必需）：存储库当前是否可用并且可以重新分发
- `status` （字符串，可选）：字符串状态代码，更详细地描述帐户状态。已知值包括：
    - `takendown`：由于违反条款或政策，服务提供商无限期删除存储库
    - “暂停”：“删除”的临时或有时限的变体
    - “已删除”：帐户已被停用，可能是永久停用。
    - “停用”：帐户本身临时或无限期删除所有公共数据。

当来自任何重新分发帐户数据的服务时，该事件描述了*该服务*的新状态，并且在该上下文中具有权威性。换句话说，该事件对于存储库主机和镜像来说是逐跳的。

有关更多背景信息，请参阅[帐户托管规范](/specs/account)。

### `#commit` 事件

此事件表示指定帐户已提交新的存储库。该事件通常包含存储库数据的“差异”，以 CAR 切片的形式。有关“diffs”和 CAR 文件格式的详细信息，请参阅[存储库规范](/specs/repository)。

事件字段：

- `seq`（整数，必需）：对于所有事件类型都相同
- `repo` （具有 DID 语法的字符串，必需）：与所有其他事件类型的 `did` 相同
- `time` （具有日期时间语法的字符串，必需）：对于所有事件类型都相同
- `rev` （带有 TID 语法的字符串，必需）：提交的修订版本。必须与提交块本身中的“rev”匹配。
- `since` （具有 TID 语法的字符串，可以为空）：指示先前提交的 `rev`，存储库差异包含与
- `commit` （cid-link，必需）：提交对象的 CID（在 `blocks` 中）
- `tooBig`（布尔值，必需）：该字段已弃用，但技术上仍然需要。生产者应始终将其设置为“false”，而消费者应忽略它。
- `blocks`（字节，必需）：对应存储库差异的 CAR“切片”。必须始终包含提交对象，并且 CAR 标头必须将提交块指示为第一个“根”。请参阅下面的尺寸限制注释。
- `ops`（对象数组，必需）：此提交中的记录级操作列表：创建、更新、删除的特定记录。请参阅下面的长度限制。
- `blob`（cid-link 数组，必需）：此字段已弃用，但技术上仍然需要。生产者应将其设置为空数组，消费者应忽略它。
- `prevData`（cid-link，半可选）：此存储库最后一次提交的 MST 树的根 CID。与“since”字段类似，表示之前的“rev”。尽管被标记为“可选”，但实际上是 MST 反演所必需的。

`ops` 对象字段：

- `action`（字符串，必填）：表示操作类型。其中之一：“创建”、“更新”或“删除”。
- `path`（字符串，必需）：存储库内的记录路径（集合和记录密钥）
- `cid`（cid-link，必需，可为空）：表示记录的新版本，如果记录已被删除，则表示`null`
- `prev`（cid-link，可选）：指示记录的先前版本（对于“更新”和“删除”），或未定义（对于“创建”）

当帐户存储库更改时，会广播提交事件。提交可以为“空”，这意味着实际记录内容没有更改，只有“rev”增加。它们可以包含单个记录更新或多个更新。

提交事件具有以下大小限制：

- “blocks”字节字段的硬性大小限制为 200 万字节
-“块”字段中的各个记录块具有一百万字节的硬限制
- 一次提交中最多可以包含 200 个记录操作

例如，单个提交不能包含 50 个记录操作，每个记录操作包含 60 KB：将满足操作数量和每条记录大小的限制，但“块”字段大小将太大。

### `#sync` 事件

此事件断言帐户存储库的当前状态。这可能是对状态的确认或澄清（如果没有任何更改），或者可能会将存储库重置为新状态。

事件字段：

- `seq`（整数，必需）：对于所有事件类型都相同
- `did` （具有 DID 语法的字符串，必需）：对于所有事件类型都相同
- `time` （具有日期时间语法的字符串，必需）：对于所有事件类型都相同
- `rev` （带有 TID 语法的字符串，必需）：提交的修订版本。必须与提交块本身中的“rev”匹配。
- `blocks`（字节，必需）：包含当前提交块的 CAR 切片。 CAR 标头必须将提交块指示为第一个“根”。

当帐户存储库状态已重置为新状态时，或者在存储库当前状态可能不明确的情况下，会广播同步事件。例如，数据损坏后重新激活的帐户可能会发出“#sync”事件。

请注意，存储库*内容*不包含在同步事件中：“blocks”字段仅包含存储库提交对象。下游服务需要获取完整的 repo CAR 文件才能重新同步。

### 可靠的存储库同步

如果服务接收并处理来自存储库的每条“#commit”消息，则它应该具有存储库中所有记录的完整且一致的视图。如果消息丢失或损坏，接收服务的某些记录视图可能不完整或不正确。服务如何确信它已成功同步完整的存储库？

如果接收服务维护存储库数据结构 (MST) 的完整副本，它可以应用每个“#commit”的差异并验证完整树结构的完整性。但这个过程在计算和存储方面都是资源密集型的，而且大规模时成本昂贵得不切实际。

相反，接收服务可以验证每个“#commit”差异是否与存储库的先前状态一致，从而创建验证链。每个存储库只需存储少量状态。

此过程的技巧是记录操作反转，如[存储库规范](/specs/repository) 中所述。 `#commit` 消息包含存储库差异（CAR 切片）和记录操作数组。这些操作可以针对 diff 块中包含的部分存储库树的副本反向应用。如果操作列表完整，则树的根应该恰好是存储库的前一个提交对象的根。请注意，树根（“data”字段）与签名提交对象本身的哈希值不同。 `#commit` 消息包含对先前存储库修订的引用（在 `since` 字段中），以及先前根树哈希的副本（在 `prevData` 字段中）。这些字段既未经过身份验证（签名）也未进行自认证，但它们可用于单独检查“#commit”消息的一致性。

要检查消息“链”是否一致，接收服务应跟踪每个存储库的存储库修订和树根（“数据”）。如果收到内部一致的“#commit”消息，但“since”和“prevData”引用与存储库的先前状态不匹配，则说明出现了问题。

如果发现“#commit”消息链已损坏，或者“#sync”消息表明存储库状态已更改，则服务将需要重新同步存储库。这通常意味着获取完整的回购 CAR 导出。

如果许多服务尝试同时重新同步存储库，则上游 PDS 主机可能会被“惊群”的请求淹没。为了缓解这种情况，接收服务应首先尝试从其直接上游（通常是中继实例）获取存储库 CAR 文件。这为上游提供了合并和缓存存储库导出的机会，从而分配负载。上游可以简单地使用 HTTP 重定向到 PDS 实例。

下面的“记录级同步”部分描述了用于跟踪记录状态和处理重新同步事件的设计模式。

### 消息验证清单

使用 Firehose 事件流的服务可能有不同的验证和验证需求。中介服务（如公共中继）可能会进行一些检查以减少网络滥用，但最终消费服务负责验证消息结构和验证真实性。

以下是验证规则和行为的摘要：

- 服务应独立解析每个 DID 的身份数据。他们应该忽略没有功能 atproto 身份的帐户的“#commit”和“#sync”事件（例如，缺少签名密钥，或缺少 PDS 服务条目，或 DID 已被逻辑删除）
- 直接订阅 PDS 实例的服务应跟踪哪个 PDS 对每个 DID 具有权威性。他们应该记住每个订阅 (WebSocket) 连接到的主机，并拒绝帐户的“#commit”和“#sync”事件（如果它们来自与该 DID 的当前帐户不对应的流）
- 服务应跟踪每个 DID 的帐户托管状态，并忽略非“活动”事件的“#commit”和“#sync”事件
- 服务应使用当前身份数据验证每个“#commit”和“#sync”事件的提交签名。如果签名最初无法验证，服务应刷新身份元数据，以防它最近发生更改。具有最终无效签名的事件应被拒绝。
- 服务应根据实际签名的提交对象（在“blocks” CAR 切片内）验证“#commit”和“#sync”消息字段，并拒绝值不匹配的消息
- 服务应使用记录操作 MST 反转，根据“ops”列表和“prevData”字段验证“#commit”消息“blocks”字段（CAR diff）
- 服务应拒绝任何超出合理大小限制的事件消息。
- 服务应验证存储库数据结构是否符合规范。缺少字段、不正确的 MST 结构或其他协议层违规都会导致事件被拒绝。
- 服务可以对身份、帐户、提交和同步事件应用速率限制，并限制违反这些限制的帐户或上游服务。速率限制也可能应用于恢复模式，例如导致身份刷新、丢失或无序提交的无效签名等。
- 服务应忽略“rev”低于或等于该 DID 最近成功处理的“rev”的“#commit”和“#sync”事件，并且应拒绝“rev”对应于未来时间戳的提交事件（超出几分钟的时钟漂移窗口）
- 服务应检查“#commit”事件中的“since”值，如果它与该 DID 的最新“rev”不一致，则将存储库标记为不同步
- 类似地，服务应该根据最新的提交对象“data”字段检查“#commit”消息“prevData”值
- 应具体验证记录的数据限制。包含损坏或完全无效记录的事件可能会被拒绝。例如，记录根本不是 CBOR，或者超出正常数据大小限制（例如，记录大小的一百万字节限制）。
- 更微妙的记录数据验证可能会被强制执行，也可能会被忽略，具体取决于服务。例如，记录中嵌入的不支持的 CID 哈希类型可能会被中继忽略（即使它们违反了 atproto 数据模型），但可能会导致记录或提交事件被 AppView 拒绝
- 中继（特别是）不应根据词典验证记录

## 记录级同步

索引服务通常关心处理网络中所有帐户的特定集合的所有记录。本节描述服务的设计模式，用于引导现有帐户和记录，然后维护记录粒度同步，包括重新同步事件。

该服务应跟踪通常的帐户级别状态：

- 身份解析缓存：DID文档和句柄
- 帐户托管状态：“上游”和“本地”（以支持本地删除）
- 回购同步元数据：最后修订和提交“数据”字段
- 回购同步状态

存储库同步状态字段跟踪整体处理状态：

- `desynchronized`（默认）：与当前版本不同步，需要重新同步
- `in-progress`：服务正在主动重新同步存储库
- `synchronized`：所有记录均已针对当前存储库修订进行处理

该服务还跟踪排序表中所有相关存储库和集合中记录的记录级状态：

- 存储库帐户 DID
- 记录路径（集合和记录密钥）
- 记录版本（CID）

该服务使用全网络中继消防软管。当收到“#identity”事件时，它会照常更新解析缓存。当收到`#account`事件时，它会更新帐户托管状态的“上游”部分。 `#commit` 和 `#sync` 事件的处理取决于存储库同步状态。

当同步帐户收到有效的“#commit”时，服务会处理所有记录操作，并更新记录状态表。例如，将创建的记录插入表中，将删除的记录从表中删除，更新的记录更新版本字段。

如果收到与当前存储库状态匹配的“#sync”消息，则该消息将被忽略。如果收到经过身份验证的“#sync”或“#commit”消息，表明存储库的提交同步消息链已被破坏，则存储库同步状态将更新为“去同步”。

为处于“不同步”状态的存储库接收到的任何“#commit”或“#sync”消息都将被忽略（丢弃）。处于“进行中”状态的存储库的任何事件都会排队等待处理（例如，在数据库中）。

该服务运行一个重新同步工作线程池。它们检查处于“去同步”状态的存储库，并在它们开始工作时将它们标记为“进行中”。重新同步过程是获取帐户的完整存储库 CAR 文件。然后，工作人员“遍历”解析的存储库树中的所有记录，扫描存储库的排序记录级状态表，并比较记录状态。如果一条记录存在于 CAR 文件中但不存在于记录表中，则视为创建。如果记录版本不匹配，则会作为更新进行处理。如果记录在表中，但不在 CAR 文件中，则将被视为删除。该表随着记录的处理而更新。 CAR 处理完成后，存储库同步元数据将被更新，然后该存储库的任何排队的“#commit”和“#sync”消息都会被处理。如果成功，存储库同步状态将更新为“已同步”，并且工作线程将返回到池中。

该服务可能希望将记录过滤为仅相关集合。仅需要在记录状态表中跟踪那些记录。范围内帐户的每条“#commit”消息都需要完全验证并更新存储库同步表，即使该提交不包含任何范围内记录。这是为了维护经过验证的回购状态链。

从全网络消防管道中发现帐户将导致当前活动帐户的数据得到处理。对于许多服务来说，这是一个很好的起点，但通常也需要回填以前的活动帐户，这可以通过将它们插入到状态稳定且状态为“不同步”的存储库中来完成。 `com.atproto.sync.listReposByCollection` XRPC 端点可用于获取在特定集合（词典模式）中具有记录的帐户列表（通过 DID）。

## 使用和实施指南

[帐户生命周期最佳实践](/guides/account-lifecycle) 文档提供了有关在不同场景（包括 PDS 主机之间的帐户创建和帐户迁移）期间发出的消息顺序的指导。

流事件可以跨帐户同时处理，但对于任何给定帐户，它们应该按顺序顺序处理。

事件流使用者需要跟踪并保留他们已成功处理的事件的序列号，以便在重新连接时用作游标值。他们可能希望从“高水位线”（考虑已接收但仍在处理的消息）中单独跟踪“最后接收”序列（用于在消息仍在处理时重新连接）。请注意，中继实例通常具有不同的排序偏移和消息排序，并且连接级序列与存储库级修订号不同。

## 安全问题

建议针对资源耗尽攻击采取一般缓解措施：事件速率限制、每个帐户的数据配额、数据对象大小限制和反序列化数据复杂性等。

向未知或不受信任的主机发出网络请求时应始终小心，特别是当这些主机的网络定位器来自不受信任的输入时。这包括验证 URL 不连接到本地或内部主机（包括通过 HTTP 重定向）、避免浏览器上下文中的 SSRF 等。

为了防止流量放大攻击，应由主机对出站网络请求进行速率限制。例如，从 Firehose 消费时的身份解析请求，包括 DNS TXT 流量和 DID 解析请求。

## 未来的工作

“subscribeRepos”词典可能会进行调整，删除已弃用的字段，即使这违反了词典演变规则。

存储库导出机制可能支持存储库子集的部分同步。例如，覆盖特定集合或存储库路径范围的子树 CAR 文件。

Firehose 事件流序列/光标方案可以迭代以支持分片、基于时间戳的恢复以及具有不同序列的服务器之间更容易的故障转移。

可以将完整验证的消防水带的替代方案添加到协议中。例如，简单的 JSON 序列化、按记录集合类型过滤、省略 MST 节点以及其他更改，这些更改将简化开发并减少不需要或不需要完全身份验证的用例的资源消耗。
